# AI-агент поддержки: roadmap и дизайн фаз 0–5B

Дата: 2026-07-10
Статус: утверждён концептуально, спека фаз 0/1/2A — этот документ

## Цель

Заменить статичную одноразовую генерацию подсказки полноценным human-in-the-loop агентом:
**контекст → предложение → решение оператора → фактический ответ → результат тикета → обучение и оценка.**

Агент ничего не отправляет клиенту сам — каждая подсказка проходит через оператора.
Долгосрочно: снять с оператора текстовое общение, сократить долю вопросов, требующих звонка.
Fine-tune — не сейчас; решение принимается позже по критериям (покрытие категорий,
однородность формата, доля human_verified пар, выигрыш на offline benchmark,
нерешаемость задачи через RAG+промпт). Fine-tune — для стиля/структуры/выбора действия,
не для хранения продуктовых знаний.

## Утверждённые решения (сводка)

| Вопрос | Решение |
|---|---|
| Ручные метки 👍/✏️/👎/📤 | Остаются, приоритетный сигнал; вытесняют авто-вердикт (судья пропускает размеченные) |
| Неявное difflib-обучение (topic_learning) | Убирается, заменяется ночным судьёй |
| Источник пар для оценки | Живые подсказки агента (хранятся постоянно) + ретро-майнинг всех закрытых тикетов |
| Первая подсказка | Автоматически при создании топика (как сейчас) |
| Последующие подсказки | Только по кнопке «💡 Предложить ответ» |
| Формат ответа | Адаптивный, без лимита слов (лимит ≤20 слов удаляется) |
| Записи звонков | Ручная загрузка в топик (АТС нет); привязка к тикету по топику загрузки |
| Ретро-майнинг | Все доступные закрытые тикеты (~1 000–5 000), порциями с чекпойнтами |
| ПДн | Как сейчас: тексты и транскрипты идут в Groq/Deepgram без маскирования |
| ESCALATE-категории | Фискальные операции; деньги/возвраты; удаление/потеря данных; доступы/безопасность |
| Продукт/языки | Один продукт, разные окружения клиентов (тянуть окружение в контекст); только русский |
| Результат тикета | closed + не переоткрыт 7 дней (смену статуса ловим через ticket_updated + проверка в ночном джобе) |
| Автозапуск оптимизатора промпта | Не включаем, /aioptimize остаётся ручным |

## Порядок фаз

0 → (1 + 2A параллельно) → 2B → 3 → 4 → 5B.
Обсуждение частичной авто-отправки и fine-tune — только после измеримого улучшения. Вне скоупа.

## Фаза 0 — трассировка, безопасность, baseline

Оценка и наблюдаемость строятся ДО агента, не после.

### Таблица `ai_suggestions` (одна строка = одна генерация)

Идентификация и якорь:
- `id`, `ticket_id`, `topic_id`
- `trigger_source` — `first` | `button` | `call_fixation`
- `context_until_post_id` — id последнего поста HDE на момент генерации (якорь состояния тикета;
  сейчас в `ai_feedback_pending` его нет — только текст history)

Снимок входа:
- `title`, `history` — снимок контекста на момент генерации
- `client_text` — сообщение клиента, на которое отвечаем
- `retrieved_refs` — JSON: id и score найденных knowledge_items / dialogue_pairs / wiki / транскриптов

Версии:
- `pipeline_version`, `prompt_version`, `model`

Выход агента:
- `action_type` — `ANSWER` | `ASK` | `ESCALATE` | `NO_ACTION`
- `ai_answer` (текст «Клиенту»), `ai_full_text`
- `confidence`, `confidence_reason`
- `self_check_status` — `supported` | `partially_supported` | `unsupported`

Действие оператора и факт:
- `operator_action` — `approved` | `edited` | `rejected` | `sent` | `none`
- `final_sent_text` — фактически отправленный клиенту текст (из 📤 или ручного ответа через `sent_hde_messages`)

Служебное:
- `generation_ms`, `tokens_in/out`, `error`
- `status` — `pending` | `manual` | `judged` | `stale`
- `verdict`, `verdict_detail` (JSON мульти-осевых оценок), `judge_reference_answer`, `judged_at`
- `created_at`

Хендлеры фидбека ([bot/handlers/ai_feedback.py](../../bot/handlers/ai_feedback.py)) при любой
ручной метке проставляют `operator_action` и `status='manual'`. `ai_feedback_pending`
не трогаем — продолжает обслуживать UI-состояние кнопок (TTL 24ч).

### Golden set

50–100 типовых кейсов из закрытых тикетов: предварительный отбор автоматикой
(разнообразие по type_id/темам), финальная валидация оператором. Хранение —
файл в `artifacts/` в формате существующего eval harness ([scripts/eval_prompt.py](../../scripts/eval_prompt.py)).

Baseline: текущий промпт прогоняется на golden set до включения агента.
Новый пайплайн включается в прод только при результате не хуже baseline.
Отдельный shadow mode не нужен: агент по определению только предлагает,
human-in-the-loop и есть теневой режим.

### Правила безопасности

Жёсткий `ESCALATE` (даже при высокой уверенности): фискальные операции (ОФД, чеки,
Z-отчёты, налоговая), деньги и возвраты, удаление/потеря данных (сбросы, переустановки),
доступы и безопасность (пароли, чужие учётки). Проверка — на этапе self-check,
категорийный список в конфиге промпта.

## Фаза 1 — агентный пайплайн (`bot/agent/`)

Заменяет одноразовую генерацию `generate_ticket_summary` для подсказок.
Формат «Суть / Клиенту / Памятка», постинг в топик и кнопки фидбека — сохраняются.

### Шаги пайплайна

1. **Выбор действия**: `ANSWER` (данных достаточно) | `ASK` (нужны уточнения) |
   `ESCALATE` (запрещённая категория или агент не должен решать) |
   `NO_ACTION` (клиент не задал вопроса — «спасибо», «ок»).

2. **Retrieval** с приоритетами источников (по убыванию доверия):
   1. текущая история тикета;
   2. данные конкретного клиента (custom fields HDE: окружение, модель кассы, ОФД; история клиента);
   3. база знаний (knowledge_items);
   4. проверенные dialogue_pairs (см. фазу 2B) — динамический few-shot;
   5. транскрипты текущего тикета;
   6. сырые исторические транскрипты и непроверенные ответы.

   Если исторический ответ конфликтует с актуальной базой знаний — не используется как пример.
   Few-shot: **до N** (по умолчанию 3) пар выше порога качества и сходства;
   подходящих нет — работаем без few-shot, слабые совпадения не подмешиваются.

3. **Генерация**: адаптивный ответ.
   - `ANSWER`: полное решение с шагами, готовое к отправке.
   - `ASK`: минимальный достаточный набор независимых вопросов одним сообщением, не более 4;
     если следующий вопрос зависит от ответа — только первый развилочный.

4. **Self-check** (один структурированный LLM-вызов, не каскад — объём 20–25 тикетов/день):
   - извлечение фактических утверждений из ответа;
   - для каждого — есть ли опора в retrieved-контексте;
   - проверка запрещённых категорий;
   - соответствие формату и voice profile;
   - отсутствие противоречий с историей тикета;
   - итог: `supported` | `partially_supported` | `unsupported`.
   `unsupported` → ответ не публикуется как ANSWER, агент переходит к ASK или ESCALATE.

### Памятка оператору (расширяется)

Кроме шпаргалки: какие статьи/пары использованы, где агент сделал предположение,
какой информации не хватает, уровень уверенности.

Модель — Groq (текущий стек), конкретная модель конфигом; версия промпта пишется
в `ai_suggestions.prompt_version` при каждой генерации.

## Фаза 2A — ретро-бэкфилл dialogue_pairs

### Таблица `dialogue_pairs`

```
pair_id, ticket_id,
source_message_id,          -- сообщение клиента, породившее ответ
context_until_message_id,   -- граница контекста
operator_message_id,
context,                    -- ТОЛЬКО сообщения ДО ответа оператора (без утечки будущего решения)
operator_answer,            -- фактически отправленный оператором текст
issue_type,                 -- type_id тикета
client_id,
created_at, resolved_at, resolution_status,
quality_status,             -- unreviewed | auto_accepted | human_verified | rejected | outdated | unsafe | duplicate
quality_reason,
embedding, embedding_model, -- intfloat/multilingual-e5-large, имя фиксируется в строке
content_hash                -- дедупликация
```

Отброшено из предложений ревью (с обоснованием): `final_sent_answer` — в ретро-парах
`operator_answer` и есть отправленный текст (поле живёт в `ai_suggestions`);
`verified_by` — оператор один; `product_area`/`product_version` — один продукт,
структурированного поля версии в HDE нет; `language` — только русский.

### Бэкфилл

- Источник: `get_closed_tickets_page` ([bot/hde_api.py:509](../../bot/hde_api.py)) —
  пагинация по owner_id (оператор один).
- Объём ~1 000–5 000 тикетов: порциями по ночам, рейт-лимит к HDE API,
  чекпойнт «докуда дошли» (возобновляемость).
- Нарезка на пары — локальным кодом без LLM: клиент-посты → следующий staff-пост
  (staff = `user_id == owner_id`, роли в API нет).
- Все пары создаются со статусом `unreviewed`. Инкрементально: новозакрытые
  (closed + 7 дней без переоткрытия) добавляются ночным джобом.

## Фаза 2B — quality gating и dynamic few-shot

- LLM-фильтр качества пар (свежие сразу, ретро — порциями): отсев приветствий,
  служебных сообщений, «позвоните нам» без решения, промежуточных ответов,
  макросов без содержания, устаревших инструкций → `quality_status` + `quality_reason`.
- `auto_accepted` пары становятся кандидатами few-shot; `human_verified` — при ручном
  подтверждении (кнопкой из сводки, опционально).
- Подключение dynamic few-shot к пайплайну фазы 1 (до этого агент работает без него).
- Закрытый тикет ≠ правильный ответ: фильтр обязателен до использования пары.

---

## Фаза 3 — multi-turn по кнопке

- Кнопка «💡 Предложить ответ» в топике. Хендлер: свежая история тикета из HDE
  (`get_ticket_posts` + comments) + транскрипты тикета → пайплайн фазы 1 →
  пост в топик с кнопками 👍/✏️/👎/📤.
- Каждая генерация — строка в `ai_suggestions` с `trigger_source='button'`
  и актуальным `context_until_post_id`.

---

## Фаза 4 — звонки (Deepgram)

- Привязка транскрипта к тикету: детерминированная, по топику загрузки
  (запись грузится в топик конкретного тикета → `topic_id → ticket_id`).
  Механизмы link_confidence/очередь несвязанных не нужны до появления АТС.
- Новая таблица `ticket_transcripts(ticket_id, transcript, summary, created_at)`;
  индексация в базу знаний сохраняется.
- После транскрипции агент предлагает **ответ-фиксацию** (только предложение,
  не авто-отправка), структура: что выяснили / что сделали / что должен сделать клиент /
  что должна сделать поддержка / сроки и обещания / нерешённые вопросы.
  `trigger_source='call_fixation'`.
- Транскрипты тикета входят в retrieval multi-turn подсказок (приоритет 5).

## Фаза 5B — ночной судья

- Ночной джоб: подсказки со `status='pending'`, чьи тикеты closed + 7 дней без переоткрытия.
  Тикет не закрыт 30 дней → `stale`. Лимит 50 тикетов/ночь, очередь через LLM_SEMAPHORE,
  ошибки парсинга → ретрай следующей ночью, после 3 попыток → `stale`.
- Вход судьи: вопрос клиента + подсказка + весь диалог до закрытия.
- Выход: мульти-осевые оценки (`verdict_detail` JSON) — правильность, подтверждённость
  источниками, полнота, полезность, безопасность, стиль, корректность уточняющих вопросов,
  совпадение с фактическим результатом; агрегированная категория
  `match|partial|miss` — только для сводки.
- `judge_reference_answer` — извлечённый (цитируемый, не сочинённый) фактический ответ
  оператора из диалога; НЕ смешивается с human_verified эталоном.
- Маппинг в `optimization_samples`: match→accepted, partial→corrected
  (op_answer=judge_reference_answer), miss→rejected. Ручные метки вытесняют:
  `status='manual'` судья пропускает.
- Неявное difflib-обучение (`_implicit_feedback`, [bot/topic_learning.py](../../bot/topic_learning.py)) отключается.
- Утренняя сводка в Telegram: разобрано/совпало/частично/мимо, stale и pending,
  2–3 примера «мимо» с причинами, недельный тренд. Калибровка судьи — на golden set.

---

## Метрики успеха

- Доля подсказок, отправленных 📤 без правки (целевой рост).
- Тренд вердиктов судьи по неделям.
- Доля тикетов, решённых текстом без звонка.
- Baseline на golden set: новый пайплайн ≥ старого до включения.

## Вне скоупа

Авто-отправка ответов клиенту, fine-tune, интеграция АТС, оценки клиентов (в HDE их нет),
маскирование ПДн, мультиязычность.
