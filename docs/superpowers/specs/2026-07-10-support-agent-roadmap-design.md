# AI-агент поддержки: roadmap и дизайн фаз 0–5B

Дата: 2026-07-10
Статус: ревизия 2 (внесены 17 правок архитектурного ревью), спека фаз 0/1/2A — этот документ

## Цель

Заменить статичную одноразовую генерацию подсказки полноценным human-in-the-loop агентом:
**контекст → предложение → решение оператора → фактический ответ → результат тикета → обучение и оценка.**

Агент ничего не отправляет клиенту сам — каждая подсказка проходит через оператора.
Долгосрочно: снять с оператора текстовое общение, сократить долю вопросов, требующих звонка.
Fine-tune — не сейчас; решение принимается позже по критериям (покрытие категорий,
однородность формата, доля human_verified пар, выигрыш на offline benchmark,
нерешаемость задачи через RAG+промпт). Fine-tune — для стиля/структуры/выбора действия,
не для хранения продуктовых знаний.

## Утверждённые решения (сводка)

| Вопрос | Решение |
|---|---|
| Ручные метки 👍/✏️/👎/📤 | Главный сигнал: `human_label` хранится отдельно, судья её не перезаписывает; `effective_label = human_label ?? judge_label` |
| Ночной судья | Оценивает ВСЕ завершённые подсказки (и с ручными метками — иначе selection bias в трендах) |
| Judge-результаты в обучение | Автоматически НЕ идут: `source='judge'`, оптимизатор использует ручные + human_verified; judge-сэмплы — после выборочной ручной проверки |
| Неявное difflib-обучение (topic_learning) | Убирается, заменяется судьёй |
| Первая подсказка | Автоматически при создании топика |
| Последующие подсказки | Только по кнопке «💡 Предложить ответ» |
| Формат ответа | Адаптивный, без лимита слов (лимит ≤20 слов удаляется) |
| Записи звонков | Ручная загрузка в топик (АТС нет); привязка по топику загрузки; транскрипты — ticket/client-scoped, в общую базу НЕ индексируются сырыми |
| Ретро-майнинг | Все закрытые (~1 000–5 000), порциями с чекпойнтами |
| ПДн → Groq/Deepgram | Без маскирования (статус-кво); но данные НЕ передаются между клиентами (scoping retrieval) |
| ESCALATE | Двухуровневый: программный pre-check до генерации + post-check в self-check; объяснение/диагностика допустимы, решения с последствиями — эскалация |
| Продукт/языки | Один продукт, разные окружения клиентов (окружение — в контекст); только русский |
| Результат тикета | closed + не переоткрыт 7 дней (ticket_updated + проверка статуса в ночном джобе) |
| Автозапуск оптимизатора промпта | Не включаем, /aioptimize остаётся ручным |

## Порядок фаз

0 → (1 + 2A параллельно) → 2B → 3 → 4 → 5B.
Частичная авто-отправка и fine-tune — только после измеримого улучшения. Вне скоупа.

## Фаза 0 — трассировка, безопасность, baseline

Оценка и наблюдаемость строятся ДО агента, не после.

### Таблица `ai_suggestions` (одна строка = одна генерация)

Идентификация и якорь:
- `id`, `ticket_id`, `topic_id`
- `trigger_source` — `first` | `button` | `call_fixation`
- `context_until_post_id` — id последнего поста HDE на момент генерации
- `idempotency_key` = hash(`ticket_id` + `trigger_source` + `context_until_post_id` + `pipeline_version`),
  UNIQUE-индекс — защита от дублей по вебхуку/кнопке/ретраю

Снимок входа:
- `title`, `history`, `client_text`

Трассировка retrieval (воспроизводимость):
- `retrieval_query`, `retrieval_config_version`, `embedding_model`
- `retrieved_refs` — JSON-массив: `{source_type, source_id, rank, score, content_hash, title, used_excerpt}`.
  Полный документ не храним; использованный фрагмент + hash — да (источник может измениться после генерации).
  `source_version` не вводим: knowledge_items не версионируются, `content_hash` покрывает задачу.

Версии:
- `pipeline_version`, `prompt_version`, `model`

Выход агента:
- `action_type` — `ANSWER` | `ASK` | `ESCALATE` | `NO_ACTION`
- `ai_answer`, `ai_full_text`
- `confidence`, `confidence_reason`
- `self_check` — JSON: `{status: supported|partially_supported|unsupported, fallback_action, fallback_client_text}`

Статусы — пять независимых измерений (не один `status`):
- `generation_status` — `running` | `completed` | `failed`
- `review_status` — `pending` | `approved` | `edited` | `rejected`
- `delivery_status` — `not_sent` | `requested` | `sent` | `failed`
- `evaluation_status` — `pending` | `judged` | `skipped` | `failed` | `stale`
- `freshness_status` — `current` | `superseded` | `stale`

Итоговые денормализованные поля:
- `final_sent_text`, `final_sent_post_id`, `reviewed_at`, `sent_at`

Метки качества:
- `human_label` (из ручных действий оператора), `judge_label`, `judge_detail` (JSON мульти-осевых оценок),
  `judge_reference_answer`, `judged_at`
- `effective_label` — вычисляется как `human_label ?? judge_label`

Служебное: `generation_ms`, `tokens_in/out`, `error`, `created_at`.

### Таблица `ai_suggestion_events` (событийная модель действий оператора)

Действия не взаимоисключающие (✏️ → правка → 📤 → sent/failed), одно поле их теряет.

```
id, suggestion_id, event_type, payload, hde_post_id, created_at
```

`event_type`: `approved` | `edit_started` | `edited` | `rejected` |
`send_requested` | `sent` | `send_failed` | `manual_reply_matched`.

Хендлеры [bot/handlers/ai_feedback.py](../../bot/handlers/ai_feedback.py) пишут события
и обновляют денормализованные поля. Метрика «отправлено без правки» = `sent` без
предшествующего `edited` по событиям. `ai_feedback_pending` не трогаем (UI-состояние кнопок).

### Идемпотентность и свежесть

- UNIQUE по `idempotency_key`: повторный вебхук/клик не создаёт дубль.
- Перед публикацией подсказки в топик — повторная проверка последнего post id тикета.
  Изменился → `freshness_status='superseded'`, не публикуем; одна автоматическая
  перегенерация с новым якорем.

### Feature flags и kill switch

Конфиг: `AGENT_ENABLED` (kill switch → мгновенный возврат к текущему `generate_ticket_summary`),
`AGENT_PIPELINE_VERSION`, `AGENT_AUTO_FIRST_SUGGESTION_ENABLED`,
`AGENT_DYNAMIC_FEWSHOT_ENABLED`, `AGENT_CALL_FIXATION_ENABLED`.
Опционально при включении: короткий canary — агент на части тикетов, остальным старый пайплайн.

### Golden set (с защитой от contamination)

- 50–100 кейсов: авто-отбор кандидатов (разнообразие type_id/тем) + ручная валидация оператором.
- Хранение: неизменяемая версия датасета в `artifacts/` + список `ticket_id` golden set.
- На каждый кейс: ожидаемый `action_type`, человеческий эталон или rubric.
- **Contamination-защита**: при evaluation из few-shot/retrieval-индекса исключаются
  ВСЕ пары тикетов golden set (не только конкретная пара), плюс общий запрет
  same-ticket retrieval (см. фазу 1).
- Оценка по осям, не одним числом. Критерии запуска нового пайплайна:
  - safety regressions = 0;
  - unsupported factual claims ≤ baseline;
  - action accuracy ≥ baseline;
  - answer usefulness ≥ baseline.
  Средний балл не может скрыть ухудшение безопасности.

### Безопасность: два уровня

1. **`pre_generation_policy_check` — код, до генерации.** Правила: keyword/rule-список
   явных запретных намерений + категория из triage-шага. Решение об ESCALATE принимает
   код по правилам, а не инструкция в промпте (промпт — не жёсткое ограничение).
   Полностью детерминированной классификации текста не существует — жёсткость в том,
   КТО принимает решение (код), а не в способе детекта.
2. **`post_generation_safety_check`** — в составе self-check, страхует результат модели.

Категории уточнены (иначе агент бесполезен для типовых кассовых вопросов):
- **Допустимо**: объяснение и диагностика — значение ошибки ОФД, причины, что проверить.
- **ESCALATE**: финансовые решения (возвраты средств, тарифы, обещания);
  изменение фискальных параметров и юридически значимые действия (перерегистрация ККТ и т.п.);
  необратимые действия (удаление данных, сбросы, переустановка с потерей);
  выдача/смена доступов и всё про чужие учётки.

## Фаза 1 — агентный пайплайн (`bot/agent/`)

Заменяет одноразовую генерацию для подсказок. Формат «Суть / Клиенту / Памятка»,
постинг в топик и кнопки фидбека — сохраняются.

### Порядок этапов (retrieval ДО выбора действия)

Определить «хватает ли данных для ANSWER» до поиска нельзя, поэтому:

1. `pre_generation_policy_check` (код) + первичный triage
   (`NO_ACTION` может определиться рано — «спасибо», «ок», — но финальное решение после контекста).
2. Сбор контекста тикета (ContextBuilder, см. ниже).
3. Retrieval (со scoping-правилами, см. ниже).
4. **Финальный выбор действия**: `ANSWER` | `ASK` | `ESCALATE` | `NO_ACTION`.
5. Генерация:
   - `ANSWER`: полное решение с шагами, готовое к отправке;
   - `ASK`: минимальный достаточный набор независимых вопросов одним сообщением, ≤4;
     развилка → только первый вопрос.
6. Self-check — **один структурированный LLM-вызов** (вариант A, без каскада):
   извлечение фактических утверждений → опора в retrieved-контексте → запрещённые
   категории → формат/voice profile → противоречия с тикетом. Возвращает сразу:
   `{status, fallback_action, fallback_client_text}` — при `unsupported` публикуется
   готовый fallback (ASK/ESCALATE) без повторной генерации.
7. Публикация с проверкой свежести (см. фазу 0).

### ContextBuilder (бюджет контекста)

Весь тикет + история клиента + KB + пары + транскрипты не влезут в контекст для длинных
тикетов. Состав с токен-бюджетом на каждый тип источника:
- исходный вопрос тикета; последнее сообщение клиента; последние N сообщений;
- краткое состояние тикета (что уже сделано);
- релевантные ранние сообщения (по необходимости);
- ограниченное число retrieval-фрагментов на каждый scope.

Вложения: изображения — через vision (как сейчас); прочие (логи, файлы) — агент видит
только метаданные (имя, тип) и обязан не делать вид, что знает содержимое.

### Retrieval: области поиска (scoping)

Три изолированные области — данные не передаются между клиентами:
- `global_knowledge` — общая база знаний, wiki; только обобщённые/проверенные знания;
- `client_scoped_knowledge` — данные и история конкретного клиента (`client_id` match);
- `ticket_scoped_transcripts` — сырые транскрипты, только `ticket_id`
  (для истории клиента — `client_id`) match.

Приоритеты источников (по убыванию доверия): история тикета → данные клиента →
global KB → проверенные dialogue_pairs → транскрипты тикета → сырые исторические
(только в рамках своего scope). Конфликт исторического ответа с актуальной KB →
исторический не используется как пример.

**Запрет same-ticket retrieval**: `dialogue_pairs.ticket_id != current_ticket_id` —
иначе утечка будущего ответа (reopened-тикеты, benchmark, повторная обработка, golden set).

Few-shot: до N (по умолчанию 3) пар выше порога качества и сходства;
нет подходящих — без few-shot, слабые совпадения не подмешиваются.

### Памятка оператору

Шпаргалка + основания: использованные статьи/пары, где предположение,
какой информации не хватает, уверенность.

Модель — Groq, конфигом; `prompt_version` пишется при каждой генерации.

## Фаза 2A — ретро-бэкфилл dialogue_pairs

### Таблица `dialogue_pairs`

```
pair_id, ticket_id,
source_message_id, context_until_message_id, operator_message_id,
context,                    -- ТОЛЬКО сообщения ДО ответа оператора
operator_answer,
issue_type, client_id,
created_at, resolved_at, resolution_status,
quality_status,             -- unreviewed | auto_accepted | human_verified | rejected | outdated | unsafe | duplicate
quality_reason,
embedding, embedding_model, -- intfloat/multilingual-e5-large
content_hash
```

Отброшено из ревью-предложений: `final_sent_answer` (в ретро-парах `operator_answer`
и есть отправленный текст), `verified_by` (оператор один), `product_*` (один продукт,
поля версии в HDE нет), `language` (только русский).

### Определение сообщений оператора

`user_id == owner_id` ненадёжно (владелец меняется, отвечал другой сотрудник, системные посты).
Алгоритм:
1. **До утверждения нарезки — проверить сырой JSON ответа HDE API** на наличие поля
   роли/типа автора (в `HDEPost` оно сейчас просто не извлекается — возможно, есть в ответе);
2. если роли нет — конфигурируемый список известных staff user IDs;
3. owner_id тикета — только крайний fallback;
4. посты бота и системные — явно отбрасываются.

### Бэкфилл

- Источник: `get_closed_tickets_page` ([bot/hde_api.py:509](../../bot/hde_api.py)), пагинация по owner_id.
- ~1 000–5 000 тикетов: порциями по ночам, рейт-лимит к HDE API, чекпойнт (возобновляемость).
- Нарезка пар локальным кодом без LLM; `context` строго до ответа оператора (без утечки будущего).
- Все пары — `quality_status='unreviewed'`. Инкремент: новозакрытые (closed + 7 дней) ночным джобом.

## Фаза 2B — quality gating и dynamic few-shot

- LLM-фильтр качества пар (свежие сразу, ретро порциями): отсев приветствий, служебных,
  «позвоните нам» без решения, промежуточных, макросов без содержания, устаревших
  инструкций → `quality_status` + `quality_reason`.
- `auto_accepted` — кандидаты few-shot; `human_verified` — при ручном подтверждении
  (кнопка из сводки, опционально).
- Подключение dynamic few-shot к пайплайну фазы 1 (до этого — без few-shot).
- Закрытый тикет ≠ правильный ответ: фильтр обязателен.
- Пары тикетов golden set в few-shot индекс не попадают.

## Фаза 3 — multi-turn по кнопке

- Кнопка «💡 Предложить ответ» в топике: свежая история из HDE + транскрипты тикета →

- `trigger_source='button'`, актуальный `context_until_post_id`, идемпотентность по ключу.

## Фаза 4 — звонки (Deepgram)

- Привязка транскрипта детерминированная — по топику загрузки (`topic_id → ticket_id`).
  Механизмы link_confidence/очередь несвязанных не нужны до появления АТС.

### Таблица `ticket_transcripts`

```
id, ticket_id, topic_id,
source_post_id, source_attachment_id,   -- откуда запись (несколько звонков на тикет)
transcript, summary,
utterances_json, speaker_mapping,       -- diarization Deepgram, заполняется по возможности
provider, model, language,
processing_status, error,
content_hash, created_at
```

- **Изоляция**: сырой транскрипт в общую базу знаний НЕ индексируется
  (изменение текущего поведения [bot/transcription.py](../../bot/transcription.py)) —
  только `ticket_scoped_transcripts`. В `global_knowledge` попадают только обобщённые
  синтезированные знания без клиентских деталей (существующий wiki/knowledge-пайплайн).
- Ответ-фиксация после транскрипции — только предложение (не авто-отправка);
  структура: что выяснили / что сделали / что должен сделать клиент /
  что должна сделать поддержка / сроки и обещания / нерешённые вопросы.
  `trigger_source='call_fixation'`.
- Транскрипты тикета — в retrieval multi-turn подсказок (свой scope).

## Фаза 5B — ночной судья

- Ночной джоб: подсказки с `evaluation_status='pending'`, чьи тикеты closed + 7 дней
  без переоткрытия. Тикет не закрыт 30 дней → `stale`. Лимит 50 тикетов/ночь,
  LLM_SEMAPHORE, ошибки парсинга → ретрай следующей ночью, после 3 попыток → `failed`.
- **Судья оценивает ВСЕ завершённые подсказки, включая размеченные вручную** —
  иначе selection bias: тренд отражал бы только проигнорированные оператором подсказки.
  Ручную метку судья не перезаписывает: `human_label` и `judge_label` хранятся отдельно,
  `effective_label = human_label ?? judge_label`. Расхождения человек/судья — материал
  для калибровки судьи.
- Вход: вопрос клиента + подсказка + весь диалог до закрытия.
  Выход: `judge_detail` (оси: правильность, подтверждённость источниками, полнота,
  полезность, безопасность, стиль, корректность уточняющих вопросов, совпадение
  с фактическим результатом) + агрегированная категория `match|partial|miss` для сводки +
  `judge_reference_answer` (цитируемый из диалога фактический ответ оператора, не сочинённый).
- **В обучение автоматически не идёт**: judge-результаты пишутся в `optimization_samples`
  с `source='judge'`; оптимизатор промпта по умолчанию использует только ручные метки
  и `human_verified`. Judge-сэмплы допускаются в обучение после выборочной ручной
  проверки (`eligible_for_optimization=true`). Фактический ответ оператора не обязательно
  правильный (обходное решение, устаревшая инструкция).
- Неявное difflib-обучение (`_implicit_feedback`, [bot/topic_learning.py](../../bot/topic_learning.py)) отключается.
- Утренняя сводка: разобрано/оси/категории, stale и pending, расхождения с ручными
  метками, 2–3 примера «мимо» с причинами, недельный тренд. Калибровка судьи — golden set
  + расхождения с human_label.

## Метрики успеха

- Доля подсказок, отправленных 📤 **без правки** (по событиям: `sent` без предшествующего `edited`).
- Тренд `judge_label` по неделям (без selection bias — судятся все).
- Доля закрытых тикетов **без зарегистрированного звонка** (честное имя: запись грузится
  вручную, отсутствие транскрипта не доказывает отсутствие звонка).
  Опционально: кнопка «📞 Был звонок» в топике для точного учёта.
- Baseline на golden set: критерии запуска из фазы 0 (safety = 0 регрессий и т.д.).

## Вне скоупа

Авто-отправка ответов клиенту, fine-tune, интеграция АТС, оценки клиентов (в HDE их нет),
маскирование ПДн, мультиязычность, длительный shadow mode (короткий canary — опционален).
