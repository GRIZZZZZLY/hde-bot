# Автозаполнение полей «Приоритет» и «Тип» тикета — дизайн

**Дата:** 2026-06-12
**Статус:** утверждён пользователем

## Цель

Бот после AI-сводки автоматически выставляет в тикете HDE поля «Приоритет»
(`priority_id`) и «Тип» (`type_id`) на основе LLM-классификации переписки —
по аналогии с уже работающим автозаполнением поля «Окружение».

## Матрица правил (основа промпта)

| # | Ситуация в переписке | Приоритет | Тип |
|---|---|---|---|
| 1 | Торговля невозможна (касса/терминал не работают) | Ускоренный оборуд | Ошибка |
| 2 | Что-то сломалось, но торговля идёт (напр., принтер этикеток) | Стандарт оборуд | Ошибка |
| 3 | Приход инженера банка в магазин (вне очереди) | Ускоренный оборуд | Задача |
| 4 | Подключение, настройка, перенастройка (касса, принтер, формат этикетки, IP) | Стандарт оборуд | Задача |
| 5 | Вопрос / требуется изучение, поиск решения, доработка | Низкий оборуд | Вопрос |
| 6 | Редко: несрочная работа без чёткого SLA | Низкий оборуд | Задача |
| — | Уверенно определить нельзя | поля не трогаем | поля не трогаем |

Не используются ботом никогда: тип «Инцидент», приоритеты «1я линия основной»,
«Стандарт 2я», «Ускоренный 2я\оборуд» (вторая линия — не наша зона), «ИИ».

## Архитектура

### Классификатор

Новая функция `classify_priority_type()` в `bot/ticket_fields.py`, по шаблону
`classify_environment()`:

- Один LLM-вызов на оба поля (приоритет+тип — одно решение, комбинация).
- Groq `llama-3.3-70b-versatile`, temperature 0, фолбэк
  `meta-llama/llama-4-scout-17b-16e-instruct` (переиспользуем `_groq_classify`).
- Промпт: матрица правил, нумерованные комбинации; модель отвечает номером
  комбинации (1–6) или «НЕ ОПРЕДЕЛЕНО».
- Парсер ответа lenient (как `_parse_env_id`): первое валидное число из ответа,
  всё прочее → None. Галлюцинированные номера вне 1–6 отклоняются.
- Вход: обогащённая история (текст + Vision-описания фото + Deepgram-транскрипты)
  и тема тикета — те же данные, что уже собирает `apply_ticket_fields()`.
- Keyword pre-pass НЕ делаем (v1): отличить «блокирует торговлю» от
  «не блокирует» регулярками ненадёжно (отрицания, контекст).

### Точка вызова и политика записи

- Вызывается из `apply_ticket_fields()` после классификации окружения.
- **Один раз за жизнь тикета**: без повторной классификации при новых
  сообщениях, ручные правки оператора не перезаписываются.
- При «НЕ ОПРЕДЕЛЕНО»: поля не трогаем, в топик тихое уведомление
  «⚠️ Приоритет и тип не определены — выставьте вручную».

### Запись в HDE API

`priority_id` и `type_id` — стандартные поля тикета (не custom_fields).
Расширить `HDEApiClient.update_ticket_fields()`: опциональные top-level поля
в теле PUT `/tickets/{id}/` рядом с `custom_fields` — один HTTP-запрос на всё.

Числовые ID значений выяснены 2026-06-12 через справочные эндпоинты
`/priorities/` и `/types/` (скрипт не нужен), фиксируются константами
в `ticket_fields.py`:

- Приоритеты: «Стандарт оборуд» = 10, «Ускоренный 2я\оборуд» = 1,
  «Низкий 2я\оборуд» = 3.
- Типы: «Вопрос» = 0, «Задача» = 2, «Ошибка» = 3.

### Хранение и метрика качества

- Две новые колонки в `ticket_topics`: предсказанные `priority_option_id`,
  `type_option_id` (по образцу `env_option_id`; '' = не определено).
- При закрытии тикета — запись в `data/priority_corrections.jsonl`
  (по образцу `log_env_outcome`): предсказание vs финальное значение,
  для оценки реальной точности через 1–2 недели.

## Обработка ошибок

Как у окружения: любой сбой (Groq недоступен, HDE PUT упал, БД) логируется
warning'ом и не ломает поток AI-сводки. Never raises.

## Тестирование

TDD, по образцу тестов окружения:

- разбор ответа модели: валидный номер, мусор вокруг номера, номер вне
  диапазона, «НЕ ОПРЕДЕЛЕНО», пустой ответ;
- сборка промпта содержит все 6 комбинаций;
- `apply_ticket_fields`: выставляет priority_id/type_id при уверенном ответе,
  не трогает при None, шлёт предупреждение;
- `update_ticket_fields` с новыми top-level полями;
- существующий набор тестов (321) не ломается.

## Решения пользователя (зафиксировано)

1. «Стандарт + Ошибка» = НЕ блокирует торговлю (в исходной формулировке была опечатка).
2. При неуверенности — ничего не ставить + предупреждение в топик.
3. «Инцидент» не используется; вопросы без поломки/работ → «Низкий + Вопрос».
4. Выставление однократное, без перезаписи после ручных правок оператора.
