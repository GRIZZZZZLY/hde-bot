# HDE x Telegram Hybrid Spec

## Цель

Зафиксировать рабочую схему интеграции `HelpDeskEddy -> webhook -> Telegram bot`, в которой:

- HDE является источником бизнес-событий;
- бот управляет Telegram Topics;
- бот сам считает точные pre-SLA уведомления;
- topic создается как при назначении тикета на меня, так и при создании новой заявки, если она уже сразу назначена на меня;
- при снятии тикета с меня topic закрывается сразу и удаляется через 8 часов;
- при закрытии тикета topic удаляется сразу.

## Принятые допущения

1. Бот работает только с тикетами, которые в определенный момент были назначены на меня.
2. Все webhook-события из HDE считаются недоверенными и должны обрабатываться идемпотентно.
3. HDE может присылать повторные webhook-события, поэтому создание topic, постановка таймеров и удаление должны быть устойчивы к дублям.
4. Если topic уже существовал и был поставлен на удаление, повторное назначение на меня должно отменять удаление и переиспользовать тот же topic.

## Состояние, которое хранит бот

Для каждого отслеживаемого тикета бот хранит:

- `ticket_id`
- `unique_id`
- `topic_id`
- `ticket_name`
- `company_name`
- `priority`
- `status`
- `owner_id`
- `owner_name`

- `last_client_reply_at`
- `last_staff_reply_at`

Дополнительно бот хранит таблицу обработанных событий:

- `event_key`
- `event_type`
- `ticket_id`
- `received_at`

## Визуальный стандарт Telegram

### Название topic

Формат:

`🟡 #ABC-123 | Компания | Короткое название`

Правила:

- первая часть всегда содержит эмодзи приоритета и номер тикета;
- вторая часть содержит компанию;
- третья часть содержит краткое название тикета;
- итоговое имя обрезается до лимита Telegram.

### Эмодзи

- `🔴` критично
- `🟠` высокий
- `🟡` средний
- `🟢` низкий
- `🆕` тикет назначен на меня
- `✏️` название тикета изменилось
- `📩` ответ клиента
- `✅` ответ сотрудника
- `⏳` тикет снят с меня, topic ждет удаления
- `🗑️` topic удален
- `⏰` pre-SLA уведомление

### Формат сообщений в topic

Сообщения должны быть короткими и блочными:

- первая строка показывает тип события;
- отдельными строками идут ключевые поля;
- ссылка на HDE всегда идет отдельной строкой;
- длинный текст не дублируется, если его достаточно показать в HDE.

## Точный функциональный сценарий

### 1. Новая заявка уже назначена на меня

Источник: событие `Новая заявка` в HDE, если исполнитель уже я.

Поведение бота:

1. Получить webhook `assigned_on_create`.
2. Проверить, соответствует ли `owner_id` или `owner_name` моему профилю.
3. Если topic отсутствует:
   - создать новый topic;
   - сохранить связку `ticket -> topic`;
   - отправить стартовое сообщение `🆕 Тикет назначен на вас`.
4. Если topic уже существует:
   - не создавать новый;
   - синхронизировать данные тикета.

### 2. Назначение на меня

Источник: событие изменения исполнителя в HDE.

Поведение бота:

1. Получить webhook `owner_changed`.
2. Если новый исполнитель = я:
   - создать topic, если его еще нет;
   - либо переоткрыть topic, если он был поставлен на удаление;
   - обновить данные тикета;
   - отправить стартовое сообщение `🆕 Тикет назначен на вас` или `🆕 Тикет снова назначен на вас`.
3. Если новый исполнитель != я:
   - перейти к сценарию `Сняли с меня`.

### 3. Переименование тикета

Источник: событие изменения заявки в HDE.

Поведение бота:

1. Получить webhook `ticket_updated`.
2. Сравнить новое `ticket_name` с сохраненным.
3. Если название изменилось:
   - обновить название topic;
   - сохранить новое название;
   - отправить системное сообщение `✏️ Название тикета обновлено`.

### 4. Ответ клиента

Источник: событие `Новый ответ`, где автор последнего ответа = клиент.

Поведение бота:

1. Убедиться, что topic существует.
2. Если topic находится в состоянии `pending_delete`:
   - отменить отложенное удаление;
   - переоткрыть topic;
   - продолжить обработку.
3. Отправить сообщение `📩 Ответ клиента`.
4. Обновить `last_client_reply_at`.
5. Сбросить предыдущий pre-SLA таймер.
6. Рассчитать новый `pre_sla_notify_at`.
7. Запланировать личное уведомление в Telegram ЛС.

### 5. Ответ сотрудника

Источник: событие `Новый ответ`, где автор последнего ответа = сотрудник.

Поведение бота:

1. Отменить активный pre-SLA таймер по тикету.
2. Обновить `last_staff_reply_at`.
3. При необходимости отправить в topic системную отметку `✅ Ответ сотрудника отправлен`.

### 6. Сняли с меня

Источник: событие изменения исполнителя в HDE, при котором тикет перестал быть назначенным на меня.

Поведение бота:

1. Найти связанный topic.
2. Если topic не найден:
   - ничего не делать.
3. Если topic найден:
   - отправить сообщение `⏳ Тикет снят с вас`;
   - закрыть topic;
   - отменить активный pre-SLA таймер;
   - сохранить `delete_after_at = now + 8 hours`;
   - перевести topic в состояние `pending_delete`.
4. Если в течение 8 часов тикет снова назначается на меня:
   - отменить удаление;
   - переоткрыть topic;
   - продолжить работу в нем же.
5. Если в течение 8 часов тикет закрывается:
   - удалить topic сразу.
6. Если в течение 8 часов тикет не вернулся и не был закрыт:
   - удалить topic по таймеру.

### 7. Закрытие тикета

Источник: событие изменения статуса в HDE.

Поведение бота:

1. Найти связанный topic.
2. Отменить все таймеры.
3. Если topic существует:
   - удалить topic сразу;
   - пометить запись как `deleted`.
4. Отложенного удаления на 8 часов при закрытии быть не должно.

### 8. pre-SLA

Источник: внутренний таймер бота, а не таймер HDE.

Поведение бота:

1. После каждого клиентского ответа бот определяет:
   - общее SLA на ответ;
   - порог предупреждения, например `10 минут до нарушения`.
2. Бот рассчитывает время уведомления:
   - если SLA = `30 минут`, а предупреждение за `10 минут`,
   - уведомление ставится на `20-й` минуте после последнего ответа клиента.
3. Если до наступления таймера:
   - сотрудник ответил;
   - тикет закрыт;
   - тикет снят с меня;
   - topic переведен в удаление;
   таймер отменяется.
4. В момент срабатывания бот отправляет только в ЛС:
   - `⏰ До нарушения SLA осталось 10 минут`
   - `🎫 #номер тикета`
   - `🏢 Компания`
   - `📝 Название`
   - `🔗 Открыть в HDE`
5. В topic группы pre-SLA уведомление не отправляется.

## Правила HDE для этой схемы

Важно:

- Диспетчер HDE не гарантирует мгновенное выполнение правил;
- если в вашей конфигурации правила конкурируют между собой, порядок и приоритет надо проверить на практике;
- правило создания topic при новой заявке и правило создания topic при изменении исполнителя должны существовать одновременно.

## Почему pre-SLA должен считать бот

Условие `Минут от последнего ответа` в HDE не подходит как основной механизм pre-SLA для этого проекта, потому что:

1. правило срабатывает не точно, а в диапазоне `1-20 минут` после порога;
2. первый ответ, создавший тикет, не запускает таймер;
3. логику отмены таймера после ответа сотрудника надежнее держать в одном месте.

Следовательно:

- HDE присылает `client_reply`;
- бот сам рассчитывает точный таймер;
- бот сам отправляет ЛС.

## Правила реализации в коде

1. Любой webhook должен обрабатываться идемпотентно.
2. Повторный webhook не должен создавать второй topic.
3. Повторный webhook не должен ставить второй одинаковый pre-SLA таймер.
4. Удаление topic через 8 часов должно быть отменяемым.
5. При возврате тикета на меня должен переиспользоваться старый topic, если он еще не удален.
6. При закрытии тикета удаление всегда имеет приоритет над отложенным удалением.
7. Сценарий `assigned_on_create` и сценарий `owner_changed -> me` должны вести в один и тот же результат: активный topic.

## Безопасные ответы из topic

Для операторской работы в Telegram topic используется безопасный режим:

- обычный текст в topic не отправляется клиенту;
- `/note текст` создает внутренний комментарий в HDE;
- `/send текст` отправляет публичный ответ клиенту через HDE API;
- `/send` в ответ на сообщение отправляет текст исходного сообщения клиенту через HDE API.

Ограничения:

- команды работают только внутри активного topic;
- команды доступны только разрешенным Telegram user id;
- публичные ответы могут быть отключены глобально через конфиг;
- публичные ответы могут быть ограничены allowlist-списком тестовых тикетов.
