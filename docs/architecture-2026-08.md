## 1. Что это за система

Telegram-бот для одного специалиста 2-й линии поддержки кассового оборудования
(АТОЛ, Эвотор, Штрих-М, Viki, эквайринг Сбер/ВТБ/Т-Банк). Мост между
HelpDeskEddy (HDE) и Telegram-группой с форум-топиками.

Роль бота — **ассистент оператора, а не автоответчик клиенту**. Это главное
архитектурное ограничение, из которого выводится почти всё остальное:

- бот НИКОГДА не пишет клиенту сам; он готовит черновик, отправляет человек;
- значит, ошибка бота стоит дешево (оператор её видит), а вот навязчивость и
  шум стоят дорого → все AI-сообщения идут `disable_notification=True`, а
  «не знаю» — легальный ответ (KB-канал молчит по умолчанию, см. 7.4);
- значит, ground truth для обучения — **что оператор реально написал клиенту**,
  а не кнопки в боте (кнопки мертвы, см. 9.4);
- значит, LLM-верификация нужна не в hot path (там верификатор — человек), а в
  офлайн-контуре оценки промптов (раздел 10–11).

Что делает по факту:

1. Каждый тикет → отдельный forum topic; клиентские сообщения и вложения
   попадают туда автоматически.
2. При новом тикете — AI-подсказка из трёх блоков (Суть / Ответ клиенту /
   Памятка) с кнопками обратной связи и кнопкой «отправить в HDE».
3. Автозаполнение полей тикета в HDE (окружение, классификация, приоритет, тип).
4. Pre-SLA будильник за N минут + «reassurance» клиенту.
5. Учёт необработанных тикетов в General-топике + утренний дайджест.
6. Ежедневный отчёт в Google Sheets (Playwright по UI HDE).
7. Ночные офлайн-задачи: нарезка диалоговых пар, LLM-гейт качества пар,
   сверка «черновик бота ↔ ответ оператора», отчёт пользы.

## 2. Топология процесса и деплой

Один Python-процесс, один event loop, одна SQLite-база.

```
                    ┌───────────────────────── systemd (config1) ────────────┐
   HDE (webhook) ──► nginx ──► aiohttp :8080 ──► webhook_inbox (SQLite)      │
                                  │                    │                    │
   Telegram  ◄──── aiogram long polling ◄──── dispatcher/handlers            │
                                  │                    │                    │
                            scheduler loop      inbox worker (2 c)          │
                    └────────────────────────────────────────────────────────┘
```

- **aiogram 3.x long polling**, не Telegram-webhook: при старте
  `bot.delete_webhook()`, `_ALLOWED_UPDATES = ["message", "callback_query"]`.
  Публичный HTTPS-endpoint нужен только для HDE, дублировать его для Telegram
  смысла нет — polling убирает возню с сертификатами и потерянными апдейтами.
- **aiohttp** обслуживает `/webhook/hde` и `/health`.
- **systemd** `deploy/systemd/hde-bot.service`: `Restart=always`,
  `WatchdogSec=90`; бот сам пингует `WATCHDOG=1` каждые 30 с
  (`bot/main.py::_watchdog_loop`) — зависший event loop не «висит тихо», его
  перезапускает systemd. Тройной запас (30 против 90) — чтобы одна пропущенная
  итерация не роняла сервис.
- **Логи** пишутся в journald напрямую через `systemd-python`, а не в stdout:
  на config1 стрим `StandardOutput=journal` для этого юнита сломан и вывод молча
  теряется. Практический журнал прода — файл `/opt/hde-bot/logs/bot.log`.
- **Fail closed на старте**: без `HDE_WEBHOOK_SECRET` процесс отказывается
  подниматься (`_ensure_webhook_secret`) — открытый webhook-endpoint хуже
  выключенного бота.
- Публичный хост вебхуков — DuckDNS-домен на порту 8443 (по записи в памяти
  проекта; при смене IP нужно обновлять DuckDNS).
- Деплой: `git pull` + `systemctl restart hde-bot`. Миграций-скриптов нет:
  `init_db()` — идемпотентные `CREATE TABLE IF NOT EXISTS` плюс
  `_add_column_if_missing()`, который спрашивает `PRAGMA table_info` и добавляет
  колонку, только если её нет. Раньше на этом месте стоял
  `try/except Exception: pass` с комментарием «column already exists» — он
  одинаково глотал «колонка уже есть», занятую базу, битый файл и кончившееся
  место, и бот стартовал на неполной схеме, падая позже и в другом месте.
  Теперь «колонка есть» — это ответ PRAGMA, а настоящая ошибка летит наверх.
- Схема при этом всё равно нигде не версионируется (`schema_version` нет), и
  откат релиза откатывает код, но не данные. Компенсация — суточный снапшот
  базы (см. 13).

## 3. Приём событий: durable inbox

`bot/hde_webhook.py` + `bot/db/inbox.py` (ADR 2026-07-12).

```
POST /webhook/hde
  → проверка секрета
  → _normalize_payload() (HDE присылает поля в разных регистрах/формах)
  → _build_event_key() — детерминированный event_id
  → enqueue_event() → строка 'pending'  ─► 200 OK
  → kick: асинхронный drain_inbox()
```

**Почему не обрабатывать синхронно в хендлере.** `200 OK` означает «событие
надёжно сохранено», а не «обработано». Если обрабатывать в запросе, то любой
сбой (Telegram 5xx, таймаут HDE API, краш) теряет событие безвозвратно — HDE
не ретраит. Инбокс превращает потерю в отложенную обработку.

Модель попыток: `attempts` инкрементится **при claim** (claim = попытка);
краш оставляет строку в `processing`, её переклеймит следующий проход после
истечения lease (120 с); исчерпание 5 попыток → `dead`; backoff 30 с × n.
Дедупликация приёма — единственная, по `UNIQUE event_id` (инвариант I7):
раньше дедуп был размазан по `processed_events` и хендлерам, и повторный
webhook давал двойной топик.

Два триггера дрена: kick из вебхука (низкая латентность) и воркер каждые 2 с
(`bot/main.py::_run_inbox_worker`) — подхват после краша процесса и ретраи.
Рассчитано на одного воркера: SQLite — один писатель.

Диспетчер (`dispatch_event`) разводит события по типам:
`assigned_on_create`, `owner_changed`, `ticket_updated`, `client_reply`,
`staff_reply`, `ticket_closed`.

## 4. Слой «тикет ↔ топик»

`bot/topic_manager.py` (939 строк — самый большой модуль, ядро продукта) плюс
механически выделенные из него `topic_sla.py`, `topic_history.py`,
`topic_learning.py`, `topic_media.py`.

Ключевые решения:

- **Блокировка на тикет**: `_ticket_locks` — `WeakValueDictionary[str, Lock]`.
  HDE присылает `ticket_updated` и `owner_changed` конкурентно; без лока
  создавались два топика на один тикет. Weak-значения — чтобы словарь не рос
  вечно: запись жива, только пока кто-то держит лок.
- **Выделенные модули late-bound**: `topic_sla`/`topic_history`/`topic_learning`
  обращаются к состоянию через модуль `bot.topic_manager`, а не импортируют
  символы. Это сохранило работоспособность существующих monkeypatch-ов в тестах
  при чисто механическом выносе кода.
- **Фильтр владельца**: `config.matches_owner()` — по `HDE_OWNER_ID`, иначе по
  имени. Бот обслуживает одного специалиста; чужие тикеты игнорируются, кроме
  General-канала.
- **Цвет топика** по приоритету (`PRIORITY_COLORS`), имя топика
  `_build_topic_name` + переименование при смене темы в HDE.
- **Отложенное удаление**: закрытый тикет не удаляет топик сразу
  (`pending_delete` + `list_due_deletions`) — оператор должен успеть прочитать.

### 4.1 Pre-SLA и reassurance (`bot/topic_sla.py`)

`schedule_pre_sla` считает `notify_at` от последнего ответа клиента и SLA
тикета; планировщик за `PRE_SLA_WARNING_MINUTES` шлёт алерт (в топик или в
General), обновляет его по мере тика, снимает при ответе.

Две защиты, обе появились после ложных срабатываний:

- `PRESLA_HDE_VERIFY=1` — перед алертом проверяем через HDE API, не ответил ли
  оператор уже напрямую в HDE (`_hde_staff_replied_since`). Локальное состояние
  не знает про ответы, сделанные не через бота. Результат кэшируется в пределах
  одного прохода планировщика: три цикла могут спросить про один тикет.
- Автоответы клиента не считаются «ответом клиента» и не перезапускают таймер.

`send_reassurance_to_client` — за `REASSURANCE_MINUTES_BEFORE` минут клиенту
уходит «Я про вас не забыл». Это единственное сообщение, которое бот пишет
клиенту сам, и оно не содержит фактов — сознательно.

## 5. Поток нового тикета

```
assigned_on_create
 → _ensure_active_topic(): create_forum_topic + upsert_topic
 → _post_ticket_history(): posts + comments (🔒 для внутренних) в топик
 → AI-подсказка:
     AGENT_ENABLED=1 → bot/agent/pipeline.run_agent()   (раздел 6)
     иначе / при провале драфта → ai_summary.generate_ticket_summary() (legacy)
 → post_suggestion_messages(): три тихих сообщения с кнопками
 → register_feedback_pending(): idempotency_key = f(ticket, trigger,
       anchor_post_id, pipeline_version, prompt_version)
 → ticket_fields.apply_ticket_fields(): автозаполнение полей в HDE
```

Три сообщения, а не одно: у них разная аудитория и разные кнопки.

| Сообщение | Кому | Кнопки |
|---|---|---|
| 🧠 Суть (N%) | оператору, диагноз | 👍 / 👎 |
| 💬 Ответ клиенту | текст, готовый к отправке | 👍 / ✏️ / 👎 / 📤 в HDE / 💬 комментарий |
| 📋 Памятка | шпаргалка оператору | 👍 / 👎 |

`retry_missing_ai_summaries` добирает подсказки для топиков, где генерация не
удалась (`list_topics_missing_summary`) — LLM-канал не считается надёжным.

### 5.1 Автозаполнение полей (`bot/ticket_fields.py`)

Поля HDE: `2` окружение, `3` классификация (константа «Оборудование» = 20),
`24` роль («Не важно» = 197); плюс top-level `priority_id`/`type_id`.

- **Option-ID зашиты в код**, потому что HDE API не отдаёт списки опций
  select-полей — id вытащены сканированием 450 живых тикетов.
- **Приоритет+тип классифицируются одним вызовом** как комбо: с 2026-07-15 в
  проде валидны только 4 комбинации (`1|10` × `2|3`), и просить модель про два
  независимых поля — приглашение к невалидной паре.
- **Окружение имеет keyword pre-pass** (`_keyword_match`) до LLM. Полезно и
  опасно одновременно: 2026-08-18 Groq снял `llama-3.3-70b`, обе классификации
  начали получать 404 — но окружение выживало на regex-пути, а приоритет/тип
  отдавал `None`. Симптом «сломалось одно поле из двух» указывал не на логику
  поля, а на общий LLM-канал. Отсюда правило: сначала грепать лог на HTTP-ошибки
  провайдера.
- Исходы пишутся в `data/env_corrections.jsonl` / `priority_corrections.jsonl` —
  сырьё для будущей калибровки.

## 6. Агентный пайплайн (`bot/agent/`)

`run_agent()` (`bot/agent/pipeline.py:29`), порядок жёстко зафиксирован:

```
1. extract_client_text        — последняя реплика клиента, без HTML
2. pre_generation_policy_check — ДЕШЁВЫЙ regex-гейт ДО retrieval
      ESCALATE → memo + запись трассировки, выход (ноль LLM-вызовов)
3. build_agent_context        — история в бюджете + evidence + demos
4. generate_agent_draft       — один JSON-драфт (action/suit/client/memo/conf)
5. post_generation_safety_check(client) — второй проход по ТЕКСТУ МОДЕЛИ
6. self_check                 — опора утверждений на источники
7. freshness                  — не появился ли новый пост; ≤1 перегенерация
8. compose_memo + record_suggestion (трассировка)
```

Почему именно так:

- **Safety — в коде, а не в промпте.** `bot/agent/safety.py` — списки regex по
  категориям (`finance`, `fiscal_change`, `data_loss`, `access`). Инструкция в
  промпте «не обещай возврат денег» — рекомендация, которую модель нарушит;
  гейт в коде — инвариант. Эскалируют только действия с последствиями;
  объяснение и диагностика проходят.
- **Pre-check до retrieval.** Retrieval — это эмбеддинг + скан матрицы + BM25 +
  возможный вызов wiki. Если запрос всё равно уйдёт оператору, платить за это
  незачем.
- **Post-check по тексту модели.** Модель может выбрать `ANSWER` и в теле
  ответа предложить перерегистрацию ККТ. Проверяем результат, а не намерение.
- **`evidence` и `demos` разделены** (`context.py`). `evidence` —
  knowledge_items / wiki / solution_patterns, это grounding: self-check
  проверяет ответ ПРОТИВ ИХ СОДЕРЖИМОГО. `demos` — похожие диалоговые пары,
  это few-shot стиля. Смешивать нельзя: пара «вопрос → ответ оператора» не
  является источником фактов для другого тикета, и self-check, увидев её,
  подтвердил бы выдуманное.
- **`partially_supported` сохраняет драфт.** Раньше любой не-`supported`
  заменял ответ шаблонным уточняющим вопросом; на практике это выбрасывало
  почти готовый ответ из-за одной непокрытой детали. Теперь: пометка оператору
  «проверь факты» + `confidence ≤ 50`. Полная замена — только `unsupported`.
- **Self-check не должен переспрашивать известное.** В промпте прямо: не
  спрашивать то, что клиент уже сообщил; если факты есть — следующий шаг или
  `ESCALATE`. Это регрессия, которая ловилась в проде.
- **Fail-safe дефолт self-check** — `unsupported → ASK`: при любом сбое
  (таймаут, битый JSON) агент деградирует в уточняющий вопрос, а не в
  уверенный ответ.
- **Freshness — одна перегенерация, не цикл.** Пока модель думала, клиент мог
  написать ещё. Один повтор на свежих постах; на втором заходе — публикуем с
  пометкой «клиент прислал новое сообщение». Цикл здесь мог бы не сойтись
  никогда при болтливом клиенте.
- **JSON-override идёт ПОСЛЕДНИМ в system-промпте** (`actions.py:34`).
  Прод-инцидент 2026-07-12: активный промпт требует текстового формата
  «Суть/Клиенту/Памятка» и блока `<reasoning>`, few-shot усиливают текстовый
  вывод — без финального override qwen отвечает текстом, `parse_agent_draft`
  возвращает `None`, и агент молча падает на legacy-путь. При этом override
  меняет только ОБЁРТКУ: правила стиля и длины остаются обязательными для
  значений JSON, иначе поле «client» скатывается в «душный дефолт».
- **Провал драфта → `None` → legacy `generate_ticket_summary`.** Агент —
  надстройка, а не замена; выключается флагом `AGENT_ENABLED`.
- **Служебные строки убраны из Памятки** (`compose_memo`): «Основания: KB#…»,
  «Действие·уверенность·self-check» шумели оператору. Провенанс не потерян —
  он в `ai_suggestions`.

## 7. Контекст и retrieval

### 7.1 История в бюджете

`build_history_budgeted` (3000 симв.): первое сообщение клиента + хвост
**целыми сообщениями** + маркер «пропущено N сообщений». Резать посередине
реплики нельзя — модель достраивает обрубок и галлюцинирует.

### 7.2 Основной RAG-канал: `knowledge_items`

`bot/knowledge/store.py::find_similar`:

1. Эмбеддинги всех items кэшируются в памяти (TTL 60 с) уже распарсенными в
   `np.ndarray`, плюс стопка в матрицу с предпосчитанными нормами. `frombuffer`
   на каждый запрос и полный `sort` таблицы — то, от чего ушли; сейчас одно
   матричное умножение + `argpartition` на `limit*3`.
2. **Cosine + BM25 (FTS5), слияние через RRF (k=60)**. Только вектор
   проигрывает на коротких точных совпадениях — коды ошибок, модели касс,
   артикулы; только BM25 — на перефразированном описании проблемы. RRF
   выбран вместо взвешенной суммы, потому что не требует калибровки шкал.
3. BM25-находкам вне cosine-пула **проставляется реальный cosine-score** —
   иначе порог уверенности в `get_rag_context` убил бы именно точные
   лексические попадания.
4. **Company boost** `+1/(k+1)` — эквивалент первого места: у одной компании
   повторяются одни и те же конфигурации.
5. **Дедуп по нормализованному контенту**: в базе есть буквальные дубли под
   разными `source` — копия не должна сжигать слот в top-k.
6. `title`/`url` доклеиваются одним запросом: операторы часто решают тикет
   ссылкой, значит ссылка обязана доехать до промпта.

`RAG_MIN_SCORE = 0.83` — не «на глаз»: замер (`scripts/_measure_rag_scores.py`,
30 тикетов против 1120 items) дал релевантные top-1 в 0.88–0.96, нерелевантные
запросы ≤0.79. Пустой результат — нормальный исход, блок RAG просто исчезает
из промпта.

Эмбеддер — `intfloat/multilingual-e5-large`, 1024-dim, локально
(sentence-transformers, CPU), ленивая загрузка в executor, обязательные
префиксы `query:`/`passage:`, `normalize_embeddings=True`. Локальная модель, а
не API: эмбеддинги нужны на каждый тикет и на каждый майнинг-проход, платить
за них по сети — дорого и хрупко.

`clean_for_embedding` срезает подписи, цитаты, URL, email, «#12345» — но
**только на входе эмбеддера**; сырой контент остаётся в БД, оператор читает его
глазами.

### 7.3 wiki и solution_patterns

- `bot/wiki/` — LLM синтезирует markdown-статьи из knowledge_items
  (`data/wiki/*` + `_index.json`), поиск — по пересечению нормализованных
  токенов заголовка. Примитивно и намеренно: статей десятки.
- `solution_patterns` — типовые шаги по (оборудование, тип проблемы).
  Пополняется `/aianalyze` (батчи по 15 тикетов через LLM) и implicit feedback.
  `find_solution_pattern` + `increment_pattern_use`.

### 7.4 Канал внутренней БЗ (Teamly) — выключен по умолчанию

`indexer.get_kb_context`, `source='teamly'`, флаг `KB_TEAMLY_ENABLED`.

Отдельный от примеров тикетов канал со своим порогом и своим слотом в промпте:
справочная статья и похожий тикет — разные жанры, и статья не должна съедать
слот примера (`find_similar(sources=…/exclude_sources=…)`).

Два замера, оба важны как урок:

- `KB_MIN_SCORE = 0.85` **плюс лексический якорь**: одного абсолютного порога
  мало — настоящие top-1 лежат в 0.839–0.882, и туда же попадают заведомо
  неверные. Поэтому статья показывается только если её ещё и находит BM25
  (`fts_search_source_any_token`).
- `chunker.py`: статьи Teamly доходят до 86 KB, а `embed_text` режет вход на
  8000 символах — большей части документа для поиска просто не существовало.
  Режем по заголовкам, `TARGET_CHARS=1500`, `OVERLAP=200`. 1500 против 600 —
  замер: медиана top-1 не меняется (0.863), векторов в 2.5 раза меньше
  (956 против 2409 на 110 статьях).
- `is_navigational()` отбрасывает статьи-оглавления: плотный список ключевых
  слов бьёт настоящую инструкцию по косинусу (статья «Posiflora» — чистый
  список ссылок — забрала top-1 у 8 тикетов из 30).

Канал выключен не из-за порога, а из-за **покрытия**: выгрузка — общая БЗ
первой линии (регламенты, админка), а бот обслуживает отдел оборудования.
Ложная статья хуже отсутствующей.

### 7.5 Dynamic few-shot: `dialogue_pairs`

`bot/agent/pair_retrieval.py`, флаг `AGENT_DYNAMIC_FEWSHOT_ENABLED`.

Косинус по **problem-side** эмбеддингу (последний вопрос клиента + контекст),
`PAIR_MIN_SCORE = 0.83` — порог обязателен, слабые совпадения не подмешиваются.
Кэш кандидатов 300 с. Двухпроходный приоритет: сначала ответы **своего**
оператора, чужие — фолбэк (учимся у него, а не у отдела). Тикеты golden set и
текущий тикет исключаются — иначе оценка утекает в обучающий контекст.

## 8. LLM-слой

Единая точка входа: `ai_summary.call_groq_text` / `call_groq_json`
(+ `_call_groq_for_summary`, `_call_groq_vision_for_summary`).

- **Провайдер один — Groq**, OpenAI-совместимый эндпоинт. OpenRouter — только
  как последний резерв в оптимизаторе.
- **Модели берутся из env, не из литералов**: `GROQ_SUMMARY_MODEL`,
  `AGENT_DRAFT_MODEL` (обе `qwen/qwen3.6-27b`), `AGENT_SELFCHECK_MODEL`
  (`openai/gpt-oss-120b`). Причина — инцидент 2026-08-18: Groq снял
  `llama-3.3-70b-versatile` и `llama-4-scout` без предупреждения, и каждый
  зашитый id упал в 404 одновременно. Env-модель лечится правкой конфига и
  рестартом, без релиза. Проверять надо и дефолт в `os.getenv(...)` — мёртвая
  модель в дефолте это та же мина, отложенная до чистого деплоя.
- **`reasoning_effort` прокидывается из env** (`GROQ_REASONING_EFFORT`, на
  проде `none`): у reasoning-моделей скрытые рассуждения списываются из
  `max_tokens`, и исторический лимит вида 64 токена даёт пустой `content`.
  Параметр не универсален (`none` понимает qwen3, gpt-oss — только low/med/high),
  поэтому фолбэку на другое семейство его передавать нельзя.
- **`_strip_reasoning`** вырезает `<reasoning>` и `<think>` ДО парсинга —
  иначе числа и метки из рассуждений попадают в парсер раньше ответа.
- **`LLM_SEMAPHORE = 3`** на все исходящие LLM/Deepgram вызовы: защита от
  всплеска при пачке вебхуков.
- **Vision — фолбэк, а не основной путь**: сначала text-only вызов, и только
  если он провалился — мультимодальный (`qwen3.6-27b`, ≤3 изображения, ≤4 МБ,
  base64) с ретраями на 429/503. Картинки дороги, а нужны редко.
- **Deepgram** (`nova-2`, ru) — транскрипция голосовых клиента и записей
  звонков (`bot/transcription.py`), результат индексируется в knowledge_items.
- **Vision-RAG**: описания фото (`bot/vision.py`) дописываются к контенту
  knowledge_item перед эмбеддингом — картинка становится искомой текстом.

### 8.1 Ни одного model-id в коде + канарейка на старте

Все id моделей живут в env и нигде больше: `GROQ_SUMMARY_MODEL`,
`GROQ_VISION_MODEL` (дефолт — модель суммарки), `GROQ_CLASSIFY_FALLBACK_MODEL`,
`AGENT_DRAFT_MODEL`, `AGENT_SELFCHECK_MODEL`, `OPTIMIZER_JUDGE_MODEL`,
`OPTIMIZER_MUTATION_MODELS` (CSV), `OPENROUTER_MODEL`. Инвариант держит тест
`test_no_hardcoded_model_ids_in_modules`: он грепает `bot/` на литералы вида
`openai/gpt-oss-120b` и падает, если id снова просочился в модуль. Дефолты
разрешены только в `config.py`.

Одного env, однако, мало: неверный или снятый id виден лишь когда упадёт первый
живой запрос — в проде это тикет клиента, в оптимизаторе весь прогон. Поэтому
`bot/llm_canary.py` на старте спрашивает провайдера по одному дешёвому запросу
(`max_tokens=1`) на КАЖДЫЙ уникальный id и, если модель не отвечает, пишет
оператору в личку: что мертво, в каких оно ролях и какой переменной правится.

Два решения, без которых канарейка вредна:

- **429 — не смерть.** Free-tier штатно упирается в TPM; исчерпанная квота
  означает, что модель жива. Иначе бот кричал бы «модель недоступна» на каждом
  старте здоровой конфигурации.
- **Старт не блокируется** (`asyncio.wait_for(..., 30)`, любое исключение — в
  лог): бот без суммарки полезнее выключенного бота, а недоступный провайдер не
  повод не обслуживать тикеты. Выключается флагом `LLM_CANARY_ENABLED=0`.

Карта ролей: 4 уникальных id на 8 ролей. Локально замера нет — в `.env`
рабочей машины `GROQ_API_KEY` отсутствует, и канарейка это говорит прямо: без
ключа она пишет «проверка НЕ выполнена», а не «N моделей живы» (раньше молчала, и
нулевое число проверок читалось как зелёный отчёт).

**Первый прод-запуск 2026-08-22 сразу нашёл мёртвую модель:**

```
[ERROR] bot.llm_canary: LLM canary: groq/llama-3.1-8b-instant unavailable
(HTTP 404: The model `llama-3.1-8b-instant` does not exist or you do not have
access to it) — roles: мутации промпта
```

То есть `llama-3.1-8b-instant` снят вместе с llama-3.3 и llama-4-scout, и всё это
время `/aioptimize` молча терял одну мутацию из трёх. Живых семейств на аккаунте
два — qwen и gpt-oss; список мутаторов правится в `OPTIMIZER_MUTATION_MODELS` без
релиза.

## 9. Обучающий контур (без участия оператора)

### 9.1 Трассировка: `ai_suggestions` + `ai_suggestion_events`

На каждое предложение — строка со всем провенансом: `retrieval_query`,
`retrieved_refs` (JSON evidence+demos), `pipeline_version`, `prompt_version`,
`model`, `action_type`, `confidence(+reason)`, `self_check`, `draft_answer`
(до фолбэка self-check), `generation_ms`, плюс четыре независимых статуса
(`generation/review/delivery/evaluation`) и поля судьи.

`idempotency_key` = sha1(ticket, trigger_source, anchor_post_id,
pipeline_version, prompt_version) с UNIQUE. `prompt_version` включён
сознательно: смена промпта — новое предложение, даже если версия пайплайна не
менялась.

`draft_answer` хранится отдельно от `ai_answer`, чтобы можно было измерить,
сколько стоил фолбэк self-check.

### 9.2 Нарезка диалоговых пар (`dialogue_mining.py`)

Закрытые тикеты → пары «контекст → ответ оператора»:

- явная сортировка `(post_id, date_created)` — порядок из API не гарантирован;
- подряд идущие staff-посты склеиваются в один turn (оператор пишет в три
  сообщения);
- контекст строго ДО ответа — без утечки будущего;
- `content_hash` включает нормализованный ответ → идемпотентность прогона;
- роли раскидываются по staff-set, который **динамически резолвится** через
  `GET /users/{id}` → `group.type == 'staff'` с кэшем: команда ~10 человек и
  меняется, статический env-список ломается на новом сотруднике. В майнинге
  golden set резолвер намеренно ВЫКЛЮЧЕН — он пробивал бы каждого клиента и
  выбивал лимит HDE API.

### 9.3 LLM-гейт качества пар (`pair_quality.py`)

Закрытый тикет ≠ правильный ответ. В few-shot попадают только пары со
статусом `auto_accepted`; `rejected` (приветствия, «позвоните нам», обрывки) и
`outdated` — нет. `None`-вердикт оставляет пару `unreviewed` — доберётся
следующим прогоном, а не будет ошибочно принята. Пейсинг под free-tier: 6 с
между парами, один повтор через 30 с.

### 9.4 Ночная сверка (`reconcile.py`) — главный источник сигнала

Операторы не жмут кнопки бота и не отвечают через него: логирование фидбэка
встало 2026-06-21, `optimization_samples` почти пуст. Поэтому сигнал берётся
иначе: после смены сверяем **что бот предложил** с **тем, что оператор реально
написал клиенту в тикете**. Ноль участия людей.

Эталон — первый содержательный staff-turn с `post_id > anchor`
(`context_until_post_id`, то, что бот видел при генерации).

Две вещи, без которых сверка мерила шум (проверено на 128 сверках за 30 дней):

1. **Эталонами сплошь оказывались реплики, которые ответом не являются**:
   макрос «Примите запрос на компьютере» — 22 раза из 128, «не могу
   дозвониться», «вопрос актуален?», «Хорошо»/«🤝», маркетинговая рассылка.
   Их отсеивает `operator_text.py` ДО сравнения, и пара уходит в `skipped`, а
   не в «расхождение». Один модуль на двух потребителей (сверка и нарезка пар) —
   раньше сверка знала про макросы, а нарезка нет, и одна реплика считалась
   ответом в одном месте и мусором в другом. Чистка построчная (пост = строка)
   и фразовая внутри строки: макрос в отдельном посте отбрасывается целиком,
   склеенный с содержательным текстом — теряет только себя. Висячая пунктуация
   после выреза отличается по признаку «оторван пробелом» (мусор) против
   «приклеен к слову» (часть текста).
2. **Порог косинуса заменён LLM-судьёй с категориями.** У e5 косинус
   несвязанных текстов одного домена не около нуля, а ~0.8; все 128 сверок
   легли в 0.7524–0.9367 при пороге 0.85 — то есть «порог» стоял внутри шума, и
   пары с одинаковым смыслом получали противоположные вердикты
   (0.8673 accepted против 0.8470 corrected на одном и том же по сути ответе).
   Вместо порога — четыре категории, сформулированные как действия:
   `same_action` / `bot_escalated` (оператор решил сам, а бот отправил ждать) /
   `bot_wrong_fact` / `not_comparable`. Категория и говорит, ЧЕМ ответ другой —
   ради этого сверку и читают. `not_comparable` обязателен, иначе мусор снова
   попадает в расхождения; метку в БД он не ставит, только считается.

Маппинг в канонические метки: `same_action → accepted`,
`bot_escalated|bot_wrong_fact → corrected`. Пишутся
`judge_reference_answer`, `judge_label`, `judge_detail`, `judge_category`.

**Кандидаты в базу знаний** (`061c97f`). Вердикт `bot_wrong_fact` означает одно
из двух: в базе нет статьи по этому вопросу или статья врёт. Такая пара встаёт в
очередь `kb_candidates` (`bot/db/kb_candidates.py`) со статусом `pending`, и
кнопка в Telegram отдаёт решение человеку: «в базу» → статья индексируется через
`index_knowledge_item(source='reconcile')`, «мимо» → только статус. Автоматом не
пишем принципиально: категорию поставила модель, и её ошибка иначе уехала бы в
RAG без человеческого взгляда — то есть отравила бы источник, из которого бот
потом берёт факты. `set_kb_candidate_status` меняет статус только из `pending`,
поэтому второй клик по кнопке не пишет статью дважды. Решение вынесено в
`bot/agent/kb_candidates.py`, чтобы проверяться тестами без подделки aiogram.

### 9.5 Прочее в контуре

- **Implicit feedback (legacy, `topic_learning.py`)**: ответ оператора в топике
  сравнивается с AI через `difflib`; ≥0.7 → `implicit_good` в KB, ≥0.85 →
  усиление/создание паттерна, ≤0.35 → `implicit_corrected`. Пороги
  «на глаз» — известная слабость, живёт по инерции.
- **URL-майнинг** (`knowledge/url_mining.py`): ссылки из уже намайненных
  ответов операторов → скачивание → индексация. Ноль запросов к HDE API, дедуп
  по хэшу URL.
- **`voice_profile`**: реальные ответы оператора подмешиваются в промпт как
  образец тона (собирает `scripts/build_voice_profile.py`).
- **`value_report`**: ежедневный отчёт пользы — доля 📤 без правки, время до
  отправки. Метрики продуктовые, не LLM-оценки: они отвечают на вопрос «бот
  экономит время?», а не «бот молодец?».

## 10. Офлайн-контур оценки промптов (как есть сегодня)

Это тот контур, куда идёт правка из раздела 11.

```
ai_suggestions (с вердиктом сверки)          ← основной источник
  ├─ exclude_tickets(golden)                 ← golden остаётся audit-набором
  └─ split_samples(sha1(ticket_id) < 0.2) ──► train / holdout
        │
        ├─ evaluator.combined_score(train, prompt)        ← дешёвый прокси
        ├─ judge.holdout_score(holdout, prompt)           ← 0.5*combined + 0.5*судья
        └─ golden.evaluate_golden(cases, prompt)          ← мульти-осевой gate
```

**Источник данных — ночная сверка, а не кнопки.** `db.get_evaluation_samples`
(`EVAL_SAMPLES_SQL` в `suggestion_store.py`) отдаёт отсуженные предложения в той
же форме строки, что старый `get_optimization_samples`, поэтому evaluator, судья
и харнесс читают оба источника одинаково: `op_answer` = `judge_reference_answer`
(что оператор реально написал клиенту), `outcome` = `COALESCE(human_label,
judge_label)` — вердикт человека сильнее вердикта модели, он видел тикет.
Сэмплы без эталона или без метки не берутся: «нет данных» не должно
превращаться в «ответ плохой» (та же логика, что `not_comparable` в сверке).
`optimization_samples` остаётся резервом на машине, где сверка ещё не
отработала; источник печатается в отчёте, потому что наборы исходов разные
(сверка даёт `accepted`/`corrected`, кнопки — ещё `sent`/`rejected`) и
абсолютные скоры двух источников между собой несравнимы.

**`dataset.split_samples`**: holdout детерминирован по `sha1(ticket_id)`.
Корзину определяет ТИКЕТ, а не сэмпл: у одного тикета бывает несколько
предложений (`trigger_source` first / button / reply) с почти одинаковой
историей, и по-сэмпловый ключ (как было до 2026-08-18) разводил почти-дубли по
train и holdout — прирост кандидата на holdout мог быть переобучением на своих
же данных. Фолбэк на `id` сохранён для старых выборок без `ticket_id`. Побочный
эффект правки: состав holdout однократно поменялся, скоры до и после не
сравнимы напрямую.

**Golden set исключается из train и holdout** (`load_golden_ticket_ids` читает
`artifacts/golden/golden_tickets.txt`, файла нет → исключать нечего). Иначе
набор, по которому принимается финальное решение, постепенно превращается в
ещё один validation.

**`evaluator.combined_score`** (текущая реализация):

- вес по исходу: `sent 1.0 / accepted 0.8 / corrected 0.4 / rejected 0.0`;
- нет эталонного текста → доверяем сигналу оператора напрямую, без генерации;
- есть эталон → генерируем ответ и считаем `difflib.SequenceMatcher.ratio()`,
  `accepted = ratio ≥ 0.65` (**бинарно**);
- `_quality_multiplier`: 0.0 если нет секции «Клиенту:»; ×0.5 если короче 30%
  эталона; ×0.7 если **пересечение множеств слов** с эталоном < 0.3;
- итог `0.7 * acceptance + 0.3 * similarity` (similarity — только по
  `corrected`);
- `_MAX_EVAL_SAMPLES = 20` и `random.Random(42)`: **фиксированный сид
  обязателен** — baseline и все кандидаты должны мериться на ОДНОЙ подвыборке,
  иначе их скоры несравнимы.

**`judge.holdout_score`**: `0.5 * combined_score + 0.5 * mean(overall/10)`.
Судья — `openai/gpt-oss-120b`, **другое семейство, чем генератор qwen** —
защита от self-preference. `temperature=0`, JSON-режим, один повтор при битом
JSON. Пять булевых осей (diagnosis_correct, equipment_named, format_ok,
length_ok, sounds_human) + `overall` 0–10 + `reason`; стайлгайд
`bot/prompts/style_guide_ru.md` вклеивается в промпт судьи. Генерация
мемоизирована, чтобы `combined_score` и судья не дёргали LLM дважды на сэмпл.

**`golden.py`** — независимый замороженный датасет (Phase 0B): кейсы намайнены
из закрытых тикетов, вручную провалидированы, заморожены с `content_hash`
(`load_golden` падает, если файл правили после freeze). Оценка мульти-осевая:
`action_accuracy`, `mean_unsupported`, `mean_correctness`, `mean_usefulness` +
**код-детерминированная ось safety** (`post_generation_safety_check` по
клиентской части ответа; `_client_facing_text` отрезает reasoning и
операторские секции, иначе диагноз оператору давал ложные срабатывания).
`compare_to_baseline` — гейт: **safety-регрессии сравниваются по-кейсовому
множеству, а не по среднему** (средним нарушение скрывается), unsupported ≤
baseline, accuracy ≥, usefulness ≥. Rate-limit ретраится с backoff отдельно от
JSON-ретраев, сбой генерации изолируется по кейсу.

**`optimizer/agent.run_optimizer`**: baseline на train → мутации от 3–4 моделей
параллельно (`llm_router`, OpenRouter только если весь Groq лёг) → оценка
каждой на train → **топ-2 пересчитываются судьёй на holdout** → apply-решение
только по holdout, порог `+0.03` → все кандидаты пишутся в `prompt_versions`
(`candidate`), отчёт оператору с кнопками ✅/❌/📊.

**Ночной запуск оптимизатора ОТКЛЮЧЁН** (`scheduler.py`): источник истины —
руками настроенный `_FORMAT_INSTRUCTIONS`. Ручной прогон — `/aioptimize`.
(Докстринг `judge.py` про «ночной оптимизатор» устарел.)

**`scripts/eval_prompt.py`** — офлайн-харнесс на копии прод-базы
(`scripts/pull_kb.sh`), кеш ответов в `data/eval_cache.db` (прерванный прогон
продолжается, повторный бесплатен), режим `--no-judge`, вывод худших
регрессий по holdout. Предупреждение при <30 сэмплов.

## 11. Судья v2 (реализовано)

Источник идей — `llm-as-a-verifier`. Из трёх его приёмов применимы два.
Третий — мат. ожидание по logprob-распределению score-токенов — **недоступен
физически**: Groq возвращает **400** на `logprobs`/`top_logprobs`, и `n`
обязан быть 1 (console.groq.com/docs/openai, «Currently Unsupported»). Библиотека
`llm-verifier` не ставится: её собственный пример расхода — 24 вызова и 1.5M
input-токенов на один `select`, при нашем free-tier TPM 12000.

**Статус.** Реализовано целиком: `bot/optimizer/checks.py` (hard-checks),
`bot/optimizer/judge.py` (оси, N/A, k повторов, caps, ключ кеша),
`bot/optimizer/gate.py` (парные дельты, bootstrap, пер-осевые регрессии),
`evaluator` без jaccard и без бинарного порога, `agent.py` на гейте,
`eval_prompt.py` с кешем вердиктов и `--resample-judge`. Шаг 1 (источник данных
из сверки) — в разделе 10.

**Чего замера ещё нет.** Ни один порог в этом разделе не измерен на живых
данных: в `.env` рабочей машины нет `GROQ_API_KEY`, поэтому рубрика ни разу не
проверялась настоящей моделью. До первого прогона с ключом открыты три вещи:
парсится ли JSON рубрики у `gpt-oss-120b` (модель reasoning-семейства, ей
`max_tokens=700` может не хватить на JSON после рассуждений), какой у судьи
реальный разброс на повторах, и какими должны быть `MIN_MEAN_DELTA` и
`MAX_CI_DOWNSIDE` в `gate.py` — сейчас там заведомо консервативные заглушки,
а не результат замера. Порядок: `--resample-judge` на baseline → размах →
порог выше размаха.

**Место — судья (`bot/optimizer/judge.py`), а не train-петля.** Разделение
уровней сознательное: `combined_score` считается для КАЖДОГО кандидата и обязан
остаться бесплатным, а решение «применять или нет» принимается на holdout.
Верификация ставится туда, где принимается решение.

### 11.1 Что исправлено против первой версии этого плана

Первая версия отдавала LLM то, что проверяется кодом (формат, длина), не имела
оси полезности, не определяла `N/A`, позволяла отмыть неверный факт хорошим
стилем, сравнивала два средних и оптимизировалась на одном и том же holdout
сколько угодно раз. Ниже — версия без этих дыр.

### 11.2 Hard-checks: код, не судья

Детерминированные условия проверяются кодом и **не попадают в рубрику судьи** —
иначе платим токенами за шум и получаем субъективную оценку факта, который
проверяется regexp-ом:

| Проверка | Реакция |
|---|---|
| нет секции «Клиенту:» | кейс = 0 (структурный провал) |
| «Клиенту» длиннее лимита слов | штраф по коду, не оценка судьи |
| пустой ответ / только reasoning | кейс = 0 |
| текст `<reasoning>`/`<think>` протёк в клиентскую часть | кейс = 0 |
| safety-категория в клиентской части (`post_generation_safety_check`) | кейс = 0, кандидат помечен |

Лимит слов (сейчас 20) — продуктовое правило, поэтому проверяется прямо. Но он
**не универсален по действиям**: `ASK`, `ANSWER` и `ESCALATE` требуют разной
длины, и лимит нужно задавать по `action_type`, а не одним числом на всё.

### 11.3 Soft-оси судьи: только то, что требует смысла

```
diagnosis      1-20  верно ли понята причина (сверка с ответом оператора)
equipment      1-20  правильно назван модель/ПО                     | N/A
actionability  1-20  клиент получил конкретный следующий шаг
human          1-20  звучит как живой оператор (стайлгайд)
```

`actionability` добавлена по ревью: без неё ответ мог получить высокий балл за
верный диагноз, названную модель и живой стиль, **не дав клиенту никакого
действия**. В golden-оценке ось `usefulness` уже есть — её отсутствие у судьи
было прямой асимметрией.

**Контракт каждой оси** (обязателен, иначе судья угадывает):

```json
{"score": 1..20 | null, "applicable": true|false, "reason": "кратко"}
```

`applicable=false` → вес оси исключается из знаменателя, а не считается
нейтральным и не снижает балл. Пример: оборудование в истории не упомянуто —
`equipment` неприменим. **Обратная ошибка не является `N/A`**: если модели в
истории нет, а кандидат её назвал — это выдумка, то есть провал `diagnosis`.
То же и с диагнозом: часть тикетов требует не причины, а процедурного действия
или запроса данных — тогда `diagnosis` неприменим, а решает `actionability`.

**Якоря обязательны.** Шкала 1–20 сама по себе разрешения не создаёт: без
примеров судья просто переедет с «7 и 8» на «14, 16 и 18». Для каждой оси:

```
 1  полностью неверно или опасно
 5  крупная ошибка, отправлять нельзя
10  частично полезно, нужна существенная правка
15  хороший ответ, правка косметическая
20  корректно и готово к отправке
```

### 11.4 Нормировка, свёртка, некомпенсируемость

Нормировка — **`(score - 1) / 19`**, а не `score / 20`: иначе минимальный балл
отображается в 0.05, и «полностью неверно» перестаёт быть нулём.

Свёртка — взвешенное среднее применимых осей (диагноз тяжелее стиля). Но
**полная компенсация запрещена**: неверный факт нельзя отмыть форматом и живым
тоном. Некомпенсируемые ограничения работают так же, как по-кейсовый safety-гейт
в `golden.compare_to_baseline`:

- safety-провал → кейс `0`, независимо от остальных осей;
- грубо неверный факт (`diagnosis` в нижней зоне) → верхний потолок общего
  балла кейса;
- регрессия по критической оси относительно baseline → запрет apply, даже если
  среднее выросло.

Порядок агрегации (важен именно такой):

1. hard-checks;
2. `k` soft-оценок по применимым осям;
3. нормировка `(s-1)/19`;
4. усреднение **повторов внутри кейса**;
5. применение caps;
6. усреднение **по кейсам** (повторы не считаются отдельными примерами);
7. парные дельты candidate − baseline;
8. проверка пер-осевых регрессий;
9. golden gate.

### 11.5 k-повторов: что они дают и чего не дают

k=3 оценки на кейс, усреднение — **замена мат. ожидания по logprob выборочным
средним**, единственный доступный оценщик того же распределения.

Границы приёма, важные, чтобы не переоценить его силу:

- повторы снижают **шум судьи**, а не неопределённость датасета. 26 кейсов × 3
  повтора — это по-прежнему 26 кейсов, а не 78 независимых примеров;
- «ошибка падает как 1/√k» верно **при независимых повторах**. Ответы LLM бывают
  коррелированы, а провайдер может частично детерминировать вывод — то есть
  выигрыш на практике меньше теоретического;
- повторы имеют смысл только при `temperature > 0` у судьи (стартовая гипотеза
  ~0.6; **значение подбирается замером** по стабильности, согласию с ручной
  разметкой и частоте битого JSON). Температура генерации остаётся 0.2 — меряем
  разброс оценщика, а не генератора.

Поэтому **сохраняются не только средние**: все `k` сырых вердиктов, разброс по
каждой оси, число битых JSON, модель и параметры, latency и token usage. Без
разброса нельзя ни поставить порог, ни увидеть, что судья деградировал.

Позже — адаптивный `k`: два вызова всегда, третий только при сильном расхождении
или когда кейс близок к порогу решения.

### 11.6 Кеш вердиктов

Индекса повтора в ключе **недостаточно**: после смены рубрики или модели кеш
отдал бы старый вердикт. Полный ключ:

```
hash(ответ кандидата) | hash(эталон) | judge_model | rubric_version |
hash(style_guide) | temperature | reasoning_effort | schema_version | repeat_index
```

Плюс режим `--resample-judge`, игнорирующий кеш вердиктов: им измеряется текущая
вариативность судьи (то, что нужно для порога в 11.7).

### 11.7 Гейт: парные дельты, а не разница средних

Baseline и кандидат считаются на ОДНИХ кейсах, значит сравнивать надо
по-кейсово: `dᵢ = scoreᵢ(candidate) − scoreᵢ(baseline)`, и смотреть на
распределение `dᵢ`.

Apply разрешён при выполнении всех трёх условий:

1. средняя дельта положительна и превышает практически значимый минимум;
2. нижняя граница bootstrap-интервала не уходит в существенный минус;
3. нет критических регрессий по safety/correctness.

`_MIN_IMPROVEMENT = 0.03` уходит: он не только подобран под другую шкалу, но и
по конструкции учитывает лишь шум судьи, игнорируя разброс между кейсами,
множественный выбор кандидатов и winner's curse (мы берём максимум из
нескольких мутаций — максимум смещён вверх даже при нулевом реальном эффекте).

**Один holdout нельзя оптимизировать бесконечно.** Если `/aioptimize` гонять
много раз и читать результаты глазами, holdout становится validation. Уровни:
train (сортировка кандидатов) → holdout (выбор кандидата) → golden (редкая
финальная проверка, не используется для итеративной настройки).

### 11.8 Train-прокси: убрать сломанное, не строить второй судью

- **jaccard-гейт по множествам слов убирается**: он мерит «те же слова», а
  правильный ответ может быть сформулирован иначе;
- бинарный `accepted = ratio ≥ 0.65` → непрерывный `ratio`: порядок кандидатов
  становится гладким, стоимость не меняется (difflib бесплатен);
- структурный и длинный гейты остаются (см. 11.2).

Отдельно: `holdout_score = 0.5*combined + 0.5*judge` даёт лексическому
`SequenceMatcher` половину финального веса. Но `combined_score` несёт и
**единственный человеческий сигнал** в формуле — веса исходов
(`accepted`/`corrected` из сверки), тогда как судья сам LLM. Поэтому не
выкидываем, а смещаем к ~0.3/0.7 **после** того, как новый судья покажет
разброс меньше старого. Кандидат на замену лексической части — непрерывная
semantic similarity на уже локальной e5, без порога.

### 11.9 Контракт и совместимость

`combined_score` и `holdout_score` продолжают возвращать `float` в [0,1] —
`optimizer/agent.py`, `scripts/eval_prompt.py` и `golden.py` не меняются.
Меняются: `judge.build_judge_prompt` (рубрика + якоря), `judge.judge_answer`
(k повторов, оси, `N/A`, сырые вердикты), `judge.holdout_score` (свёртка, caps),
`evaluator._quality_multiplier` (минус jaccard), бинарный `accepted` и гейт
apply в `agent.py` (парные дельты вместо `_MIN_IMPROVEMENT`).

### 11.10 Цена

Holdout ≈ 20% выборки: ~26 кейсов × (1 baseline + 2 кандидата) × k=3 ≈
**234 вызова судьи** по ~1.5k токенов ≈ 350k токенов, плюс ~52 генерации по
~5k ≈ 260k. При реальном TPM **8000** (не 12000, см. 15) это **~1.5 часа** с
пейсингом, а не 20 минут. Приемлемо для `/aioptimize` и ночного харнесса; для
train-петли неприемлемо, поэтому она и остаётся бесплатной. Кеш вердиктов и
генераций делает повторный прогон почти бесплатным — без него итерация по
рубрике невозможна на таком лимите.

### 11.11 Тесты, без которых правку не включать

- `1 → 0` и `20 → 1` при нормировке;
- `applicable=false` исключается из знаменателя;
- критическая ошибка не компенсируется format/human;
- три повтора дают три разных ключа кеша; смена модели или рубрики
  инвалидирует кеш;
- битый вердикт: пропущенная ось, строка вместо числа, значение вне 1–20,
  один невалидный повтор из трёх;
- точное усреднение заранее заданных mock-вердиктов;
- отсутствие jaccard-понижения; монотонность непрерывного train-скора;
- парные дельты: кандидат с положительным средним, но широким разбросом, не
  проходит гейт;
- повторный baseline-прогон с отключённым кешем вердиктов (замер шума);
- согласие судьи с небольшой ручной разметкой.

Правятся: `tests/test_judge.py`, `tests/test_prompt_optimizer.py`,
`tests/test_eval_harness.py`. `tests/test_golden_set.py` не затрагивается.
`tests/test_eval_dataset.py` (шаг 1) уже в дереве.

### 11.12 Чего эта правка НЕ даёт

Не best-of-N: `generate_agent_draft` делает один черновик, и генерация N
кандидатов в проде не влезает ни в TPM, ни в латентность тикета. Не
logprob-верификатор: механизм заблокирован провайдером. Не влияет на рантайм
бота — только на офлайн-оценку промптов. Если понадобится настоящий verifier,
нужен провайдер с logprobs (DeepSeek API — заявлен, проверить прямым вызовом)
или локальный vLLM (GPU; у нас CPU-only) и только в офлайн-контуре.

## 13. Планировщик (`bot/scheduler.py`)

Один цикл, `SCHEDULER_INTERVAL_SECONDS=30`, окно срабатывания по MSK ±5 мин
(`_hm_matches`) — попадание «в минуту» ненадёжно при дрожании цикла.

| Когда | Что |
|---|---|
| рабочий день, digest-час | flush General → дайджест → value-report → digest сверки (порядок важен: flush первым, чтобы счётчик в дайджесте был после сверки) |
| каждые ~7 мин в рабочее время | сверка General с HDE — ловит назначения, сделанные прямо в HDE (webhook приходит с пустым owner_name) |
| Пн–Чт 8:30 MSK | кнопка «сделать отчёт за прошлый рабочий день» |
| Пн–Чт 9:00 MSK | автозапуск отчёта, если кнопку не нажали |
| Чт 19:00 MSK | вечерний автозапуск отчёта |
| Вс 8:30 MSK | недельная сводка |
| раз в час | GC `topic_media_cache` (>1 ч) |
| ночью | инкремент `dialogue_pairs` (cutoff 7 дней) |
| ночью | сверка ответов (`reconcile_recent`) |
| 01:xx UTC | снапшот базы `VACUUM INTO backups/hde_bot-YYYY-MM-DD.db` |
| Вс 00:xx UTC | expiry knowledge_items старше 180 дней |
| рабочее время | pre-SLA алерты, reassurance, отложенные удаления топиков |
| каждый проход | алерт на события инбокса в статусе `dead` |
| — | ночной prompt-оптимизатор ОТКЛЮЧЁН (только `/aioptimize`) |

### 13.1 Изоляция джобов

Все задачи прохода идут через `_run_job(name, coro, timeout=…)`: 90 с обычному
джобу, 600 с ночным пачкам и `VACUUM INTO`, 120 с блоку таймеров. Причина не в
аккуратности, а в том, что проход СЕРИАЛЕН: один зависший `await` (HDE API без
ответа, Telegram, браузер) останавливал всё, включая pre-SLA-будильники. Watchdog
это не ловит — он отдельный таск и продолжает пинговать systemd, поэтому процесс
выглядит здоровым, пока таймеры молчат. Таймаут снимает зависшую корутину и
пишет в лог `ERROR`, проход идёт дальше.

Прогоны отчёта уходят в **фон** (`_spawn_report`): Playwright открывает браузер
и ходит по UI HDE — это минуты, а в том же проходе стоят таймеры. Single-flight
обязателен: два браузера на один профиль конкурируют и падают оба, поэтому
повторный запуск, пока предыдущий жив, отбрасывается.

Pre-SLA, обратный отсчёт, reassurance и отложенные удаления вынесены в
`_process_due_timers` — самая чувствительная к задержке часть прохода получила
свой таймаут и не зависит от остальных джобов.

`_maybe_alert_dead_inbox` сообщает про строки инбокса в статусе `dead`: это
webhook, который не обработался за все попытки — клиент написал, а топик не
появился, и SLA идёт молча. Единственный сбой инбокса, невидимый вообще никак.
Алерт по РОСТУ счётчика (иначе повторялся бы каждые 30 с), а число уже
разосланных лежит в `bot_settings`, не в памяти: строки `dead` переживают
рестарт, и in-memory guard кричал бы про старые события при каждом подъёме.

Всё, что шлёт сообщения, проходит через `work_schedule`: `WORK_DAYS=0,1,2,3,6`
(Пн–Чт + Вс), 9–18 MSK, плюс режим отпуска (`/vacation Nd`), который
персистится в `bot_settings` и восстанавливается при старте.

## 14. Отчётность

`bot/reporting/`: Playwright логинится в веб-интерфейс HDE, снимает два отчёта
(staff_user_report — количество тикетов и среднее время; глобальный — счётчик
«Сгорел» по SLA), затем `gspread` пишет строку в Google Sheets.

UI-автоматизация, а не API, потому что этих агрегатов в HDE API нет. Цена
решения: хрупкость к вёрстке и требование браузеров для того пользователя, под
которым идёт процесс — бот работает как root, и после апгрейда Playwright надо
переустанавливать браузеры именно для root, иначе «Chromium is not installed».

## 15. Ограничения, о которые уже спотыкались

- **HDE API: 300 req/min → бан на 20 минут на ОБЩЕМ аккаунте**, роняющий
  сторонние интеграции. Клиентский троттл `HDE_API_MAX_RPM=120` держится ниже с
  запасом; массовый майнинг живого API запрещён, ретрай на бане — тоже.
- **Groq free-tier TPM 8000** на `qwen/qwen3.6-27b` (не 12000 — то был лимит
  снятой llama-3.3; замер по `x-ratelimit-limit-tokens` и по телу 429/413 в
  прод-логе). Узкое место всех батчей: одна генерация суммарки ≈5000 токенов,
  то есть ~1–1.5 вызова в минуту. Ночь НЕ помогает — лимит per-minute, а не
  контеншен с продом. Отсюда пейсинг в `pair_quality` (6 с), `reconcile`
  (4 с + повтор через 30 с), backoff в `golden`, кеш в `eval_prompt`.
  Отдельный симптом того же лимита: тикет с длинной историей получает **413
  Request too large** (запрошено 9685 > лимита 8000) и остаётся вообще без
  суммарки — видно в логе 2026-08-20 по тикету 193783.
- **Модели снимают без предупреждения** — закрыто: id только в env (дефолты
  тоже проверять), инвариант держит тест, снятая модель обнаруживается
  канарейкой на старте (8.1).
- **`journalctl -u hde-bot` на config1 сломан** (хостовая аномалия) — читать
  `/opt/hde-bot/logs/bot.log`.
- **`optimization_samples` устарел**: фидбэк-логирование встало 2026-06-21,
  живой сигнал даёт ночная сверка (9.4), а не кнопки.
- **KB-канал Teamly выключен** по покрытию, не по порогу.
- Флаги агента (`AGENT_*`) в коде по умолчанию `False`; фактические значения —
  в проде в `.env`, в репозитории их нет.

### 15.1 Осознанно принятые риски

Названы в архитектурном ревью, разобраны и оставлены как есть — с причиной, а не
по недосмотру:

- **Инбокс даёт at-least-once, а не exactly-once для внешних эффектов.** Краш
  между отправкой в Telegram и отметкой `completed` приводит к повторной
  обработке. Окно закрыто частично: `get_topic` дедупит топик,
  `idempotency_key UNIQUE` дедупит строку предложения; худший исход — дубль
  сообщения в топике при редком краше, и его видит единственный оператор. Полный
  журнал эффектов (`planned → executing → confirmed`) — недели работы против
  косметической проблемы. Пересмотреть, если появится второй потребитель или
  автоотправка клиенту.
- **Схема БД без версий.** `schema_version` + forward-only миграции не введены —
  для одной инсталляции это оверкилл. Дешёвая часть сделана: слепые
  `except Exception: pass` на `ALTER TABLE` заменены проверкой `PRAGMA` (см. 2),
  и появился суточный снапшот.

  **Снапшот делается `VACUUM INTO`, а не `cp`.** Копия файла живой базы содержит
  страницы в разорванном состоянии и рассогласованный с ними WAL — то есть
  «бэкап», который окажется мусором ровно тогда, когда понадобится. `VACUUM INTO`
  снимает согласованный снапшот силами SQLite. Замер на прод-копии: 243 МБ →
  241 МБ за 9,1 с, `PRAGMA integrity_check = ok`. Сжатия практически нет — база
  почти целиком эмбеддинги float32; поэтому копий держим 3, а не 7
  (`DB_BACKUP_KEEP`), старые удаляются ДО снятия новой, и если после этого
  свободного места меньше запаса ×1.3 — снапшот не делается вовсе: заполненный
  диск останавливает запись в SQLite, то есть останавливает бота. База в
  режиме WAL, поэтому девятисекундное чтение не блокирует запись вебхуков;
  задача всё равно стоит на 01:xx UTC — тихий час.

  Провал бэкапа уходит оператору в личку (максимум раз в сутки): молчаливо не
  сделанная копия хуже отсутствующей — о ней узнают в момент, когда она
  понадобилась.
- **Тяжёлые задачи живут в том же процессе** — и остаются в нём. Hot path
  (inbox worker, polling) от них не зависит: это отдельные таски. Реальную
  связку — сериализацию внутри прохода планировщика — закрыли таймаутами на
  джоб и выносом отчёта в фон (13.1), без второго процесса. Не закрыто: общий
  `LLM_SEMAPHORE` на 3 (ночная пачка и живой тикет делят лимит) — отдельный
  семафор для batch стоит сделать, когда ночные задачи начнут мешать.
- **`topic_manager.py` на 939 строк не разбирается на сервисы.** Работает,
  покрыт тестами, поддерживает один человек; сервисный рефакторинг — churn без
  выгоды.
- **Наблюдаемость точечная.** Из предложенной программы метрик сделано то, что
  имело ценность: алерт на `dead`-события инбокса (потерянный webhook =
  потерянный тикет = SLA) и `ERROR` в логе на каждый таймаут джоба. Остальное —
  по мере боли; счётчики уже есть в `bot/metrics.py`, `/health` и
  `count_inbox_by_status`.
- **URL-майнинг без сетевого allowlist.** Ссылки берутся из ответов
  **операторов** (staff-авторство), не из клиентских сообщений, поэтому
  SSRF-риск третьего порядка: атакующий = сам оператор. Domain-allowlist —
  желателен, приоритет низкий.
