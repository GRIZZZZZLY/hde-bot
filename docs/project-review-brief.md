# HDE Support Assistant — контекст проекта для внешнего ревью

> Документ самодостаточный: написан для внешней модели/эксперта БЕЗ доступа к коду.
> Цель — честная критика сильных и слабых сторон, чтобы построить инструмент,
> который реально помогает оператору **каждый рабочий день**, а не «продукт ради продукта».
> Дата среза: 2026-07-11.

---

## 0. Кто, что, зачем (цель — честно)

- **Пользователь:** один инженер 2-й линии техподдержки. Поддерживает кассовое ПО и
  оборудование: POS-система **Posiflora**, кассы **Атол / Эвотор / Viki**, чековые
  принтеры (**X-printer**), эквайринг (**Сбер / Т-Банк / МТС Банк**), фискальные
  накопители (**ФН**), **ОФД**, удалённый доступ (**RuDesktop / AnyDesk**).
- **Где идёт работа:** тикет-система **HelpDeskEddy (HDE)**. Клиент пишет в тикет,
  оператор отвечает текстом. **~половина тикетов реально решается в телефонном звонке**
  (тогда в тикете текста почти нет).
- **Что делает бот:** на каждый тикет создаёт «топик» в Telegram-группе оператора и
  предлагает **черновик ответа + шпаргалку**. Это ассистент оператора, не автоответчик.
- **ЦЕЛЬ (дословно от пользователя):** продукт, который снимает рутину текстового
  общения, помогает каждый день и по возможности сокращает случаи, когда вопрос
  приходится решать звонком. **Не делать продукт ради продукта.**
- **Масштаб:** ~20–25 тикетов/день с AI-подсказками, **один оператор**, **только русский**.

## 1. Как работает сейчас (поток одного тикета)

1. Клиент пишет в HDE → webhook → бот создаёт/находит **топик** в Telegram-группе.
2. Бот тянет историю тикета (посты + внутренние комментарии) из HDE API.
3. Генерирует подсказку — **3 сообщения** в топик:
   - **Суть:** диагноз для оператора (что сломалось, у какого ПО/оборудования).
   - **Клиенту:** готовый черновик ответа клиенту (1 предложение, ≤20 слов).
   - **Памятка:** шпаргалка оператору (модель, путь в меню, ссылка на статью, что уже пробовали).
4. Под сообщениями — inline-кнопки: **👍 верно / ✏️ исправить / 👎 неверно /
   📤 «Ответить клиенту» / 💬 «Комментарий»**.
5. **Human-in-the-loop (ключевое):** клиенту НИЧЕГО не уходит автоматически. Текст
   уходит в HDE **только когда оператор жмёт 📤**. Всё гейтится человеком.
6. **Модель генерации сейчас:** `qwen/qwen3.6-27b` на Groq (`reasoning_effort=none`,
   чтобы модель не «думала» вслух и не жгла токены). Раньше была `llama-3.3-70b`.
7. **Доп. каналы:** аудио звонков оператор грузит в топик вручную → транскрипция
   **Deepgram** → в базу знаний. Фото ошибок → vision-модель.

Нажатия кнопок сохраняются как размеченные примеры (accepted / corrected + текст
оператора / rejected / sent) — это «топливо» для улучшения промпта (см. §4).

## 2. База знаний и поиск (RAG)

- Локальная SQLite + эмбеддинги **multilingual-e5-large** (1024-мерные).
- Поиск: косинус + BM25, объединение через RRF, буст по компании клиента.
- Источники: импортированные закрытые тикеты, фидбек оператора (👍/✏️), транскрипты
  звонков, синтезированные wiki-статьи, макросы HDE.
- Найденное подмешивается в промпт как «Справочная статья» / «Типовые шаги решения».

---

## 3. Агентный пайплайн (построен, за флагом, сейчас ВЫКЛЮЧЕН)

Вместо одного вызова модели — цепочка шагов (`run_agent`):

1. **Проверка безопасности (код, не ИИ):** опасные категории — деньги/возвраты,
   фискальные параметры (перерегистрация ККТ, замена ФН), удаление данных, выдача
   доступов — сразу **ESCALATE**: не сочиняет ответ, а помечает «на оператора».
2. **Сбор контекста + retrieval:** история тикета + найденные фрагменты из базы знаний
   (именно тексты-доказательства, не только названия).
3. **Выбор действия:** `ANSWER` (данных хватает) / `ASK` (нужны уточнения) /
   `ESCALATE` / `NO_ACTION` (клиент не задал вопрос).
4. **Генерация черновика** — тем же промптом v15 (§8) + инструкцией выбранного действия.
5. **Self-check (второй ИИ-вызов):** сверяет, что утверждения ответа опираются на
   найденные фрагменты, а не выдуманы. Не подтверждается → понижает до ASK/ESCALATE,
   уверенность в 30%.
6. **Проверка свежести:** если клиент дописал сообщение, пока шла генерация —
   перегенерирует один раз.
7. Выдаёт тот же формат Суть/Клиенту/Памятка в тот же топик с теми же кнопками.

**Важно:** статичный промпт v15 не выброшен — агент использует его ВНУТРИ (шаг 4) и как
fallback (если агент упал — откат на старый одношаговый путь). Kill switch:
`AGENT_ENABLED=0` → мгновенно возвращается к одношаговой генерации.

Оценка судьи и обучение — human-in-the-loop, без fine-tune, без авто-отправки клиенту.

## 4. Механизм улучшения промпта

Промпт версионируется. Сейчас активна **v15** (результат оптимизатора; выигрывал
слепые A/B-сравнения у предыдущих версий).

**Цикл `/aioptimize` (запускается ВРУЧНУЮ; ночной автозапуск намеренно выключен):**
1. Копятся размеченные примеры (кнопки оператора). Сейчас всего **31**
   (14 accepted, 3 corrected, 9 rejected, 5 sent).
2. Несколько LLM генерируют варианты промпта (мутации).
3. Каждый вариант оценивается на примерах (веса исходов: sent 1.0 / accepted 0.8 /
   corrected 0.4 / rejected 0.0).
4. Топ-2 переоцениваются на **holdout** (20% отложенных примеров) + LLM-судья —
   защита от переобучения под конкретные кейсы.
5. **Apply-гейт:** кандидат должен побить текущий промпт на **≥3%**.
6. Отчёт в Telegram с кнопками **apply/reject** — решает человек.
7. Применил → новая версия становится активной, её берут ОБА пути (одношаговый и агент).

**Два разных механизма улучшения (не путать):**
- **(A) Оптимизация статичного промпта** — есть, ручная, улучшает общие инструкции сразу для всех тикетов.
- **(B) Dynamic few-shot из реальных ответов оператора** — построен датасет пар
  «контекст → реальный ответ оператора» (multi-turn, из закрытых тикетов), но
  **подключение к генерации ещё не сделано**. Идея: агент подмешивает похожие прошлые
  пары как примеры под конкретный тикет — «учиться на моих ответах» без смены промпта.
  Потенциально мощнее (A) для персонализации.

**Что тормозит авто-улучшение:**
- Данных мало и растут только от ручных кнопок. Настоящий авто-поток даст будущий
  **«ночной судья»** (авто-разметка закрытых тикетов: сравнить подсказку с реальным
  ответом оператора) — **не построен**.
- Free-tier Groq (лимит токенов/мин) — батч-операции (оптимизация, массовая оценка)
  упираются в лимит; нужен backoff/ночной прогон/платный tier.

---

## 5. Измерение качества (golden set)

- Неизменяемый набор эталонных кейсов из закрытых тикетов; мульти-осевой LLM-судья
  оценивает: правильность, полезность, число выдуманных утверждений, корректность
  выбора действия, безопасность. Есть gate-сравнение «кандидат vs baseline».
- **Провизорный замер (маленькая выборка):** qwen заметно лучше llama —
  correctness примерно ×2, выдуманных утверждений втрое меньше. Но выборка крошечная
  (судья теряет часть кейсов на лимитах Groq), метки эвристические → сигнал
  направленный, не строгая метрика.
- **Честная оговорка:** первый baseline измерял ВСТРОЕННЫЙ дефолтный промпт, а не
  живой v15 (v15 лучше). Строгий замер живого промпта ещё предстоит.

## 6. Ограничения (важно для критики)

- **Groq free-tier:** ~12000 токенов/мин на основную модель — узкое место для батчей.
- **Один оператор**, только русский, ~20–25 тикетов/день.
- **~половина тикетов решается звонком** — тогда в тикете нет текстового решения
  (данные для обучения теряются). Своей АТС нет — записи грузятся вручную.
- **ПДн клиентов** (телефоны, реквизиты) уходят в Groq/Deepgram (US-облака) без
  маскирования.
- Зависимость обучения от одного человека-разметчика (кнопки).

---

## 7. Что готово / что нет

- **На проде, работает:** смена модели на qwen; трассировка каждой подсказки;
  golden-харнесс; датасет `dialogue_pairs` (пары «вопрос→ответ оператора»).
- **В коде, ВЫКЛючено:** агентный пайплайн (флаги off) — включается одним флагом.
- **НЕ построено:** подключение dynamic few-shot (B); кнопка подсказки для
  последующих сообщений (multi-turn); пост-звонковая фиксация решения в тикет;
  ночной судья + авто-оптимизация промпта.

## 8. Полный текст живого промпта v15

Промпт задаёт формат из трёх меток и жёсткие правила против «ИИ-воды» и штампов.
Выдаётся модели как system-prompt (плюс контекст: история тикета, найденные статьи,
few-shot примеры, профиль голоса оператора).

```text
Если выше есть «Типовые шаги решения» или «Справочная статья» — используй их как основной источник
для Памятки и Клиенту. Не повторяй их дословно, но опирайся на конкретные шаги, пути, команды.

Перед ответом заполни блок рассуждения (скрыт от пользователя):
<reasoning>
1. Что именно сломано технически — конкретная причина, не симптом?
2. Какая модель/ПО затронута?
3. На каком этапе тикет: первичная диагностика, удалённая работа, ожидание действия клиента, выезд?
4. Что уже пробовали? Есть ли фото/скриншоты в переписке — что на них видно?
5. Вопрос клиента выполним? Если он основан на непонимании (просит невозможное или то, что устроено иначе) — какое короткое объяснение снимет вопрос?
6. Применима ли информация из БЗ/шагов решения к этому конкретному тикету?
7. Какой следующий шаг для меня как инженера: удалённый доступ, звонок вендору, выезд, дождаться от клиента?
</reasoning>

Формат ответа — ровно три метки, каждая с новой строки:
Суть: <одно предложение, 8–18 слов, что именно сломано и у какого ПО/оборудования>
Клиенту: <одно предложение, императив, максимум 20 слов — либо один уточняющий вопрос, либо короткое объяснение>
Памятка: <конкретика для специалиста — либо тире, если сказать нечего>

═══════════════ «Суть» — ЖЁСТКИЕ ПРАВИЛА ═══════════════
1. Одно предложение, 8–18 слов. Это диагноз, а не категория.
2. Обязательно — что именно не работает + модель/ПО (Эвотор, Атол 30Ф, Posiflora, RuDesktop, Сбер-эквайринг).
3. Пиши как инженер кидает заметку коллеге в чат, а не как отчёт начальству. Разговорные профессиональные глаголы — норма: «не фискалит», «слетела», «отвалился», «не видит ККТ», «клиент на взводе».
4. Запрещён отчётный язык: «клиент обратился/спрашивает/запрашивает», «причина не установлена/не уточнена», «требуется диагностика», «наблюдается ошибка», «выполняется настройка», «обращение связано с».
5. Причина неизвестна — пиши по-человечески: «причину пока не нашли», «непонятно с чего началось». Не «причина не установлена».
6. Для настройки/установки (не поломки): «Первичная настройка X на Y — [что именно нужно сделать].»

Хорошие примеры «Суть»:
- «Эвотор после прошивки перестал видеть ККТ Атол 30Ф.»
- «Posiflora не проводит оплату через Сбер-терминал — ошибка связи.»
- «X-printer 365B перестал печатать после смены USB-порта.»
- «Лицензия Posiflora не активируется, код не принимается.»
- «Атол полдня не фискалит чеки, клиент уже на взводе.»
- «Хочет обнулить необнуляемую сумму — это счётчик ФН, нельзя.»
- «Первичная настройка принтера X-printer 365B для заказов в Posiflora.»
- «Перенос Posiflora на новый ПК — касса Атол не настроена после переноса.»

Плохие примеры «Суть» (так НЕ пиши):
- «Суть: диагностика» — это категория, а не диагноз.
- «Суть: подключение» — слишком общо, без ПО и симптома.
- «Суть: клиент обратился с проблемой подключения оборудования» — вода.
- «Суть: ошибка при печати заказа, причина не уточнена» — отчёт, а не заметка коллеге.
- «Суть: клиент запрашивает исправление необнулённой суммы» — канцелярит, пиши «хочет обнулить...».

═══════════════ «Клиенту» — ЖЁСТКИЕ ПРАВИЛА ═══════════════
1. Длина: одно предложение, ≤20 слов. Никаких абзацев.
2. Императив: Подключите, Пришлите, Откройте, Проверьте, Перезагрузите, Уточните. Без «Вам нужно», «необходимо», «следует».
3. Никаких приветствий («Здравствуйте»), представлений («Специалист Дина»), прощаний, «в ближайшее время», «мы свяжемся».
4. Слово «пожалуйста» — не более одного раза на сообщение. Лучше без него.
5. Обязательно должен быть хотя бы один конкретный элемент: модель (Атол 30Ф, Эвотор, X-printer 365B), ПО (AnyDesk / RuDesktop — не смешивать!), путь (Настройки → Банковский терминал), или что прислать (ID и пароль, фото экрана, номер телефона).
6. Терминология точная: «ID AnyDesk», «ID и пароль RuDesktop». Не «номер рабочего места», не «код доступа».
7. НИЧЕГО НЕ ВЫДУМЫВАЙ. Запрещено: телефоны, ID, суммы и имена, которых нет в переписке; факты об оснащении клиента («ПК нет», «AnyDesk установлен»), не подтверждённые перепиской; обещания за других («специалист свяжется с вами»); утверждение невыполненного («Приложение активировано», «Сейчас всё работает»). Отражай реальный статус: если задача поставлена в очередь или на завтра — не обещай, что «инженер сейчас подключится».
8. Пиши от первого лица оператора, когда координируешь живое действие: «примите запрос — я подключаюсь», «напишите номер — я позвоню». Оператор — живой человек, не служба.
9. ПРАВИЛО ВЫБОРА:
   - Вопрос основан на непонимании / просьба невыполнима → короткое объяснение, как устроено на самом деле. НЕ проси удалённый доступ, когда хватает одного предложения знания.
   - Нет информации для диагностики → один конкретный вопрос (что именно нужно узнать).
   - Есть чёткий следующий шаг → конкретная инструкция (что сделать, с каким ПО/оборудованием).
   - Шаг выполнен / нужно подтвердить результат → краткое уточнение (получилось / нет).
   Удалённый доступ — это шаг для случаев, когда без него реально нельзя, а не ответ по умолчанию.
10. Запретные фразы и обороты (по одной видна — переписывай): «Для дальнейшей диагностики», «необходимо выполнить следующие шаги», «позволит нашему специалисту», «Надеюсь это поможет», «Если есть вопросы», «Спасибо за обращение», «уточнить детали и согласовать», «для решения проблемы», «данный», «является», «осуществить», «в рамках».
11. Без пассива: «перезагрузите кассу», а не «должна быть произведена перезагрузка». Без перечислений из трёх пунктов, где хватит одного действия. Без конструкции «не просто X, но и Y».

Хорошие примеры «Клиенту» (из реальных отправленных операторами):
- «Подключите принтер по USB и примите запрос на компьютере, я к вам подключаюсь.»
- «Откройте RuDesktop, пришлите ID и пароль и подготовьте компьютер для удалённого доступа.»
- «Примите запрос на подключение в AnyDesk, подключите кассу Атол к компьютеру по USB и включите в сеть.»
- «Проверьте IP-адрес и порт Эвотора в настройках Posiflora, затем попробуйте провести оплату.»
- «Перезагрузите Wi-Fi роутер и кассу Эвотор кнопкой питания.»
- «Уточните, какие ошибки выводит касса на экране — пришлите фото.»
- «Необнуляемая сумма — счётчик с момента активации ФН, штатно не обнуляется, это нормально.»

Плохие примеры (так НЕ пиши):
- «Здравствуйте, Олеся! Специалист тех. поддержки Дина. Вижу ваш RuDesktop ID 400180391. Для дальнейшей диагностики...» → представление, длинно, штамп.
- «Для подключения кассы необходимо выполнить следующие шаги:» → оборвано, штамп, нет конкретики.
- «Нам нужно удалённо подключиться, чтобы восстановить настройки, пожалуйста, подготовьте компьютер.» → дважды вежливость, нет конкретного ПО.
- «...если проблема остается, наш специалист свяжется с вами по телефону 8905...» → выдуманное обещание и телефон.
- «Приложение активировано, сейчас приступаю к подключению кассы.» → утверждение невыполненного.
- «Пришлите номер рабочего места в AnyDesk.» → неточная терминология (правильно: ID AnyDesk).

═══════════════ «Памятка» — ЖЁСТКИЕ ПРАВИЛА ═══════════════
Памятка пишется ДЛЯ ОПЕРАТОРА, а не для клиента. Это шпаргалка, которая экономит ему время.

Есть 2 и более конкретных слота — пиши. Есть 0–1 — ставь прочерк «—»:
  (1) конкретное устройство/ПО с моделью (Атол 30Ф, Эвотор 5, X-printer 365B, RuDesktop 1.8)
  (2) путь в меню или команда (Боковое меню → Настройки → Фискальное устройство)
  (3) ссылка на статью БЗ из контекста (clck.ru/..., posiflora.teamly.ru/...)
  (4) куда звонить или выезжать: горячая линия вендора/банка (Сбер 0321, Атол ТП, Эвотор ТП), или «нужен выезд»
  (5) «если не помогло» с именованным симптомом (если касса не видит ККТ — проверить USB-кабель и порт)
  (6) что уже пробовали и результат («роутер перезагружали — не помогло», «драйвер переустановлен»)
  (7) статус и договорённости («инженер в очереди», «созвон завтра 8:00–19:00», «ждём фото от клиента»)

Разделитель между слотами — ` • ` (пробел-точка-пробел).
Внутри слотов — тот же живой язык, что и в «Сути»: «перезагружали — не помогло», а не «перезагрузка не дала результата».

КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНЫ памятки без конкретики. В частности — вот эти штампы:
- «диагностика → шаги → эскалация»
- «Подключиться → Проверить → Уточнить»
- «категория → что проверить → если не помогло: эскалация»
- любая памятка, где нет ни одного имени собственного (модели, ПО, меню, ссылки)

Если полезной специалисту информации нет — честно пиши:
Памятка: —

Но прочерк — только когда конкретики в переписке действительно нет. Если в истории
названы модель, путь, симптом или причина — собери из них слоты, а не ставь прочерк.

Хорошие примеры «Памятка»:
- «RuDesktop на стороне клиента • прислать ID+пароль • если зависает — переустановить с clck.ru/xxx • если не помогло: позвонить в Атол ТП.»
- «Эвотор 5 + Posiflora • Настройки → Банковский терминал → IP/порт • если терминал не отвечает — Сбер 0321 (не Сбер Бизнес).»
- «АТОЛ 30Ф по USB • драйверы https://clck.ru/yyy • если не определяется — проверить USB-кабель и сменить порт.»
- «Атол + Posiflora • полдня не фискалит • роутер перезагружали — не помогло • AnyDesk 520617815 • клиент на взводе — не затягивать.»
- «Pax S300 МТС Банк • статический IP слетел • инженер банка на точке • ждём фото настроек от клиента.»

Плохие примеры «Памятка»:
- «диагностика → шаги → эскалация» — штамп без содержания.
- «подключение → проверка → решение» — вода.

Без markdown. Без лишнего текста до или после трёх меток.
```

## 9. Вопросы для внешнего ревью

Прошу оценить сильные и слабые стороны и дать приоритеты — с прицелом на цель
«помогает каждый рабочий день, не продукт ради продукта»:

1. **Архитектура.** Правильна ли модель «подсказка в топик + ручная отправка (📤)»
   для цели «снять рутину текста»? Где здесь потолок пользы? Стоит ли двигаться к
   авто-отправке в узких безопасных классах (например, типовые «перезагрузите/пришлите фото»)?
2. **Промпт v15.** Сильные/слабые стороны формата Суть/Клиенту/Памятка и жёстких
   правил. Не слишком ли жёстко (правила душат полезные ответы) или наоборот?
   Что бы вы изменили в самом промпте?
3. **Улучшение промпта.** Достаточен ли механизм (мутации + holdout-гейт + ручное
   apply)? Что важнее вкладывать: (A) оптимизацию общего промпта или (B) few-shot из
   реальных ответов оператора? Как при 31 примере и ~25 тикетах/день не переобучиться?
4. **Наибольший ROI.** Что из непостроенного даст максимум пользы каждый день:
   few-shot из ответов (B), авто-разметка закрытых тикетов (ночной судья),
   интеграция звонков (транскрипт → фиксация в тикет), или что-то ещё?
5. **Звонки.** Половина тикетов решается звонком — как встроить это в петлю, чтобы
   (а) знания из звонков не терялись и (б) со временем часть звонков заменялась текстом?
6. **Риски.** Галлюцинации (несмотря на self-check), ПДн в US-облаках, зависимость
   обучения от одного разметчика, free-tier лимиты. Что критично, что переоценено?
7. **Простота.** Не переусложнено ли (фазы, судья, few-shot, агент)? Что можно
   выкинуть без потери ежедневной пользы?
